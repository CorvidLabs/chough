## MODIFIED

### REQUIREMENT REQ-cli-012

Local bug backlog. The helper SHALL keep each bug as one Markdown record, `.chough/bugs/<id>.md` (REQ-records-001), whose front matter gives `kind: bug`, `id`, `aliases`, `title`, `status`, `classification`, `scope`, `impact`, `criteria`, `requirements`, `cases`, `evidence` (the linked evidence IDs), `receipts` (the receipt fields of REQ-history-006 for linked evidence no longer in an open session), `regression_baseline`, `fixture`, `environment`, `revision`, `found_by` (the actor, REQ-records-007), `fixed_in`, `duplicate_of`, `related`, `created` and `updated`, where `regression_baseline`, `fixture`, `fixed_in` and `duplicate_of` are written only when set and a missing one reads as empty, and whose body gives `# <title>` and the paragraphs What happened (the symptom and actual behavior), Steps (the trigger, labelled `Trigger:`, then each step), Expected, Why it matters and Fix (`Not fixed yet.` until `chough bug update --fix <text>` sets it, each set also logged; marking a bug verified while its Fix still says `Not fixed yet.` SHALL replace that with a line naming the passing observation and its revision), then `## Log`, an append-only list with one dated entry per report, note, evidence link and status change. It SHALL list open bugs for a fresh session and SHALL search existing records by symptom, trigger and affected IDs before a new record is added. A bug SHALL remain unverified until a failed observation is linked, and a regression classification SHALL require a passed observation at an ancestor revision. A bug SHALL read as reproduced and later passed, and SHALL accept the verified status, only when a present linked passed observation was observed strictly after its most recent present linked failed observation; a receipt counts as present, and an observation shown as removed (REQ-records-009) does not. Additional evidence SHALL be appended to the Log, never overwriting anything. `chough bug add` while a session is active SHALL also add the new bug to that session's checkpoint (`checkpoint --bug`, REQ-records-004), with or without `--observation`, so the session's story names the bugs found in it and a blocking bug filed in it stops it (REQ-cli-054); with no session active, it SHALL leave every checkpoint unchanged. `chough bug update` given `--observation` with an evidence entry of the active session SHALL also add the bug to that session's checkpoint. A bug in another tool's behaviour MAY be closed as `fixed-upstream` with `bug update --status fixed-upstream --note <text>`, the note naming the upstream fix and who checked it where; it is a closed status, as `verified`, `duplicate` and `wont-fix` are, needs no Chough observation, and SHALL never read as verified by Chough. The helper SHALL render a report candidate and SHALL NOT publish it. Every new bug SHALL be named by REQ-records-003 from its title, the same for manual `bug add` and automatic failure capture, and written by create-new; an update SHALL NOT rename the record, even when its title has changed. Every `BUG-NNNN` and `BUG-<slug>-<hex>` ID from 0.5.x SHALL resolve as an alias, and duplicate and related links SHALL resolve in either direction across aliases and new names. Documentation SHALL state that Chough 0.5.x cannot read 0.6.0 bug records. Trace: FLOW-8, LIFE-5, LIFE-8, DRIVE-25, DRIVE-27.

Acceptance Criteria
- A sample failure becomes a reproduced and classified bug; a second report of the same symptom is found by search and its evidence is appended to the Log.
- A regression classification without a passed observation at an ancestor revision is refused.
- An out-of-scope bug stays in the open backlog without changing the checkpoint scope.
- Rendering a report candidate prints Markdown and performs no network action.
- A pass observed before, or in the same second as, the latest linked failure leaves the bug reproduced and the verified status is refused; a bug with no linked failure cannot be marked verified.
- `--classification blocking` is refused with a hint to use `--scope`, and `--scope product-defect` with a hint to use `--classification`.
- Manual `bug add` and automatic failure capture both name the bug `<date>-<title slug>`, and changing a stored title and then updating its status or evidence leaves the name unchanged.
- Each update appends one Log entry and leaves every earlier Log line, and every body paragraph a person wrote, byte-identical.
- A migrated bug answers to its `BUG-NNNN` alias in list, search, show, update and report, and duplicate and related links resolve from alias to new name and back.
- After the session holding a bug's linked evidence is archived, the bug resolves that evidence to the story's receipt and its verified state is unchanged.
- The CLI documentation says Chough 0.5.x cannot read 0.6.0 bug records.
- `bug update --status fixed-upstream` without a note is refused; with one it closes the bug, `bug list` shows it closed as fixed upstream, and nothing reports it verified.
- A new bug's Steps start with `Trigger:` and the trigger; `bug update --fix <text>` sets the Fix paragraph and logs it; a bug marked verified with no Fix set says which observation passed at which revision instead of `Not fixed yet.`
- A bug added while a session is active, with or without `--observation`, is in that session's checkpoint and in its archived story; a bug added with no session active is in no checkpoint.
- A bug updated with `--observation` naming an evidence entry of the active session is in that session's checkpoint; one naming another session's entry leaves the active checkpoint unchanged.

### REQUIREMENT REQ-cli-054

Bug value, deduplication and report mappings. `chough bug add` and `chough bug update` SHALL accept exactly the six classifications (unclassified, product-defect, regression, environment, requirement-gap, evidence-gap), the three scopes (blocking, in-scope, out-of-scope) and the eight statuses (open, investigating, fix-pending-verification, verified, deferred, duplicate, wont-fix, fixed-upstream), and SHALL refuse any other value naming the allowed ones, with nothing written; `fixed-upstream` SHALL be accepted only with a `--note` that is not blank (REQ-cli-012). Four statuses are closed: verified, duplicate, wont-fix and fixed-upstream. A bug SHALL block a session leaving test only while its scope is blocking, its status is not closed, and it is related to that session. Related means the session lists the bug, the bug's evidence contains a link starting with that session's id, or the bug and the session share a criterion, requirement, or case. An open blocking bug that is not related SHALL NOT stop the session, and `chough next` SHALL name it and say that it does not block this session. `chough bug add` while a session is active SHALL put the new bug on that session's bugs list (REQ-cli-012), so a blocking bug filed in a session stops it even when it names nothing else. A blocking bug that names no criterion, requirement, case, or evidence, and is on no session's bugs list, such as one filed with no session active, stops no session and is named the same way. A bug in a closed status never blocks. Search SHALL score the word overlap of a report with each bug's title, symptom and trigger, adding 0.25 when they share a criterion, requirement or case; it SHALL list matches from 0.2 and refuse a new bug only from 0.5, naming `chough bug update <id> --observation <id> --note <text>` and `--distinct <why this is a different defect>`. A distinct reason SHALL NOT be blank and SHALL be kept in the new bug's notes. A duplicate or related link SHALL name another existing bug: a link to the bug itself or to an unknown bug, and an update or report of an unknown bug, SHALL be refused with nothing written, naming `chough bug list --all`. Changing the status of a duplicate bug SHALL clear its `duplicate_of` link and record that in its notes, so a mistaken duplicate can be reopened. Marking a bug verified without a linked failure and a later linked pass SHALL name `chough bug update <id> --observation <id>`. The report candidate SHALL show every stored field, and `none recorded` (for steps, `Not recorded.`) for each empty one. Trace: FLOW-8, LIFE-5.

Acceptance Criteria
- Each classification, scope and status is accepted on add or update and recorded; any other value is refused with the allowed list and the record stays byte-identical; `--status fixed-upstream` without a note is refused with nothing written.
- Of every scope and status, only an open bug with scope blocking that is related to the session is listed as blocking and stops that session leaving test. An open blocking bug related to neither of two sessions does not stop the other, and `chough next` on that session names it as not blocking this session. A blocking bug that names nothing, added while one session is active, stops that session and not the other; one added with no session active stops neither, and `chough next` names it as not blocking. Making a related blocking bug wont-fix or fixed-upstream releases the gate.
- A report sharing only a requirement with a bug is listed by search at 0.25 and added without `--distinct`; one sharing its words is refused, naming both ways forward; a blank distinct reason is refused with nothing written, and a given one is kept in the new bug's notes.
- Linking a bug to itself or to an unknown bug, as duplicate or related, and updating or reporting an unknown bug, are refused with nothing written and name `chough bug list --all`, which lists the bugs.
- A bug marked duplicate by mistake is reopened with `chough bug update <id> --status open`, which clears `duplicate_of` and notes it; marking it verified without a linked failure names `chough bug update <id> --observation <id>`, and linking a failure and a later pass then verifies it.
- The report shows every stored field of a fully recorded bug, and `none recorded` (for steps, `Not recorded.`) for each empty one.
