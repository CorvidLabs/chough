## MODIFIED

### REQUIREMENT REQ-cli-021

Focused next action. `chough next` SHALL print a compact action view, separate from the full `chough status` report: the objective; the current stage with its status, iteration and side-stage callers; the recorded native change with its read state, summary state, approval and correction validity, terminal evidence validity, native next action and approved-delta result; the next valid action with its reason and, when one applies, its command; the gate for the next main stage; awaiting-human gates; blockers; the checkpoint's open questions; open acceptance-blocking bug IDs with the count of other open bugs; only the referenced observations that need attention, each once: those that are not current, leaving out a superseded run, an earlier run of a case whose later run the checkpoint also references, with counts for the rest, superseded runs counted apart; the most recent checkpoint decisions, at most 5 with their total, showing the kind and reason of entries that follow the `decided:`, `rejected:` or `failed:` prefix convention and other entries whole; the latest failed observation by its recorded observation time, with the status of each bug that links it; and a pointer to each module's native lesson source with the count and bounded paths of archived SpecSync lesson bundles, without reading lesson text or tracking which bundles were folded; the bundles named SHALL be the newest 3 by recorded finalization timestamp, then directory, with an unreadable timestamp sorting oldest, the same 3 that `knowledge/index.md` links (REQ-cli-043). `chough status` SHALL report the same open questions, all of them, in its checkpoint section. It SHALL print text by default and the same fields as JSON with `--json`, and each form SHALL be at most 16384 bytes, with every list bounded, its total stated and any truncation marked. The same records SHALL give byte-identical output; ordering SHALL use recorded fields and names, never file modification times. At plan, while the native change waits for its definition approval, the next valid action SHALL name the human scope gate, opened with `chough checkpoint --awaiting-human "<gate>" --drives approve` when none is open and closed with `chough checkpoint --close-gate` and the human's decision, and neither form SHALL pass on SpecSync's own next action, `specsync change approve <id> --actor <name>`, so no agent is routed to approve its own scope; an approval on authority the human gave in advance stays as REQ-cli-029 describes. Likewise at accept, neither form SHALL pass on SpecSync's own next action for the review, `specsync change review <id> --reviewer <name>`, in any field, the native summary and the gate to done included, so no agent is routed to review its own work; where they show SpecSync's next action there, it SHALL read as the human's review at the review gate. `chough next` and `chough status` SHALL derive the next valid action from the same rules and SHALL each make at most one native status read. The move into done archives the session (REQ-history-006), after which `chough next` says there is no open session and names `chough session new <key>`, exiting 0, since that is the normal state after done. A session stays open at done only while an authorized release is still ahead or unfolded inbox entries keep it open; then, when the recorded native change is archived with authenticated terminal evidence or no native change is recorded, the next valid action SHALL name, release first, `chough stage enter release --reason "<request>"` while an authorized release is still ahead, even with inbox entries unfolded, since the session archives itself only at the move from release into done; otherwise, while inbox entries are unfolded, including after that move, it SHALL name `chough inbox fold`, then `chough doctor --fix`. It SHALL do so rather than repeat the checkpoint's next action, and SHALL NOT recommend a stage reset. A stage reset SHALL replace the checkpoint's next action. In an earlier main stage, when the recorded native change is archived with authenticated terminal evidence and no pause, human gate or blocking bug applies, the next valid action SHALL NOT continue the stage; it SHALL say the change is archived and recommend the new cycle, a stage reset that carries a reason followed by a new native change, except at accept, where it SHALL recommend recording done first, with `chough stage advance`, which archives the session. An archived change finalized no later than the latest reset, or reached directly by one, is the previous cycle's: before done the action SHALL keep the reset's guidance and, when the next gate is refused, name `specsync change new`, never the archived refusal or another reset. With no native change recorded, a refused `refused:no-native-change` gate SHALL name `specsync change new`, not a bare status read. The next valid action SHALL guide a fresh agent through every stage (#76): right after `chough init` at intent with no criteria referenced, it SHALL say to capture or read the intent and name `hi check`, then `chough context`; at test, it SHALL name `chough cases select` and `chough cases run` for the selected cases, and `chough bug add` for a referenced case whose latest run failed with no bug, and once every referenced case's latest run passed and no blocking bug is open, it SHALL name `chough stage advance` to accept instead, the checkpoint's own next action shown as a sentence of its own; at accept while the native change is verifying, it SHALL say the human reviews next and SHALL never suggest an agent review: for a decision to ship it SHALL name `chough change ship <id> --close-gate "<gate>"` with the relay of REQ-cli-050, which runs the review as the human, ships and closes the gate only after the native ship (REQ-cli-059), so nothing under `.chough/` changes between `change check --commit` and finalize; for a decision not to ship, `chough checkpoint --close-gate` with `--verdict block`; with no review gate open it SHALL first name `chough checkpoint --awaiting-human "<review>" --holds accept --drives review` and, while SpecSync's verification counts Chough's records (REQ-records-014), SHALL say to commit that gate and run `chough change check <id>` again before the ship; and the waiting action for an open review gate SHALL name the same ship. A gate close that leaves no open gate holding the current stage (REQ-cli-050) SHALL set the checkpoint's next action to the step that decision allows, and `chough next` SHALL never name itself as the next action: `chough stage advance` after an approval or the close of a gate that drives nothing, `chough change ship <id>` after a review pass, `chough stage back --to build` after a review block, and, after a `--no-native` close, recording the next action the decision calls for with `chough checkpoint --next-action`. A stage move SHALL replace a next action that a gate close set, as a reset does, with `Continue <stage>` for the stage it reaches, so the step a close named never outlives the move that carried it out and `chough next` derives the next step from the stage reached. At accept while the native change is approved or implementing, the next valid action SHALL name the review preparation of the workflow's accept step in order, `chough change check <id> --no-commit` first when the change's deltas add or modify requirements, then the affected cases, the review gate, the commit and `chough change check <id>`, and SHALL NOT show a refused gate or a bare native status read as the action; while the latest run of a case the checkpoint references is not current, as after that first check materializes the requirement text, it SHALL name rerunning those cases with `chough cases run` before it names opening the review gate. A command that `chough next` or `chough status` shows, in the next valid action, a gate or a refusal, SHALL appear whole, whatever its length: a bound is met by cutting other text, never a command. `chough status` SHALL start with the same focused summary that `chough next` gives, at most 40 lines of text and a `summary` object first in JSON, before its full report, so the next action is never buried (BUG-0023). Decisions, completed work and open questions SHALL be read from the session's story sections (REQ-records-004), and corrections and the last actor shown as REQ-history-015 and REQ-records-007 say. - The view lists referenced observations that are historical, removed, ambiguous (a merge left two records with that name; the row names its places) or unavailable and counts referenced current and unreferenced ones; it carries no raw native output, no observation record and no lesson text.
- The view shows the last 5 decisions newest first with the kind and reason of prefixed entries and unprefixed entries whole; the failed observation with the greatest recorded time, ties broken by the greater observation ID, with each linking bug's status; and each module's lesson source path, at most 10 with their total, with the archived bundle count and up to 3 paths, newest finalized first, matching the lesson bundles `knowledge/index.md` links.
- Two runs over the same records, and a run after file modification times change, give byte-identical text and JSON.
- `chough next` and `chough status` report the same next valid action for the same records, and each runs `specsync change status` at most once.
- After the move into done archives the session, `chough next` says there is no open session and names `chough session new <key>`, exiting 0. A session kept open at done with an archived, authenticated change gets a next valid action that names `chough stage enter release --reason "<request>"` while an authorized release is still ahead, even with inbox entries unfolded, and otherwise `chough inbox fold`, then `chough doctor --fix`; entries still unfolded after the move from release into done keep the session open, and `next` then names `chough inbox fold`. - At intent, design, plan, build or test with an archived, authenticated change and no pause, human gate or (at test) blocking bug, the next valid action recommends the same new cycle and not `Continue <stage>`; at accept it names `chough stage advance` to done first, which archives the session.
- After a reset from done to plan, or to intent and then advance to plan, with the old change still recorded, the command is `specsync change new`, not the archived refusal or a reset; a change finalized after the reset keeps the archived guidance. With no change recorded, the plan gate's command is `specsync change new`.
- An open question recorded with `checkpoint --question`, or folded from a session inbox, appears in the text and JSON of `next`, at most 10 with its total like blockers, and in `status`; resolving it removes it from both.
