## MODIFIED

### REQUIREMENT REQ-cli-007

Canonical checkpoint. The helper SHALL keep one canonical checkpoint per open session: the front matter of the active session's `session.md` (REQ-records-004, REQ-cli-037), holding the objective, intent scope, modules, current stage with its status, iteration and side-stage callers, the native change identity, the pull request, referenced criteria, requirements, cases, design sources and files, observation and bug references, blockers, awaiting-human gates, run consents and the next action, with decisions, completed work and open questions in the story sections of the same file. `chough checkpoint --pr <number or URL>` SHALL set the pull request, one line checked as the objective is and passed through the leak guard of REQ-records-006 as the field always is, and an empty value SHALL clear it; like `--objective` and `--title`, it SHALL add no Timeline entry. No other writable checkpoint store SHALL exist and no adapter such as APS SHALL be required. Every read SHALL validate the front matter's keys and value types and SHALL refuse a malformed one naming the file, the key and the rule (REQ-records-001). `chough checkpoint --merge` and the `chough-session` merge driver are removed, because each session has its own folder and parallel branches never write one checkpoint (DRIVE-24). When SpecSync is configured, `chough checkpoint --native-change <id>` SHALL read `specsync change status <id>` before it applies any update, and SHALL refuse as `refused:native-change-unknown`, naming the ID and that status command, when SpecSync does not report the change; a failed or timed-out read SHALL also refuse, and a reply whose `summary.id` or `change.id` names a different change SHALL refuse as `refused:native-change-mismatch`, naming both IDs. A JSON reply that names neither `summary.id` nor `change.id` SHALL refuse as `refused:native-change-unknown`, since it does not identify the requested change. Every such refusal SHALL leave the session file byte-identical, including the other updates given in the same call. An ID SpecSync reports, archived or open, SHALL be saved as before. Without a SpecSync configuration only the existing ID format check SHALL apply, with no native read. `chough checkpoint --no-native-change <reason>` SHALL record, as `no_native_change` in the session's front matter, that the session's work needs no native change and why; it SHALL refuse a blank reason, SHALL refuse with nothing saved while the session records a native change, naming it, and recording a native change SHALL remove it. Reading and saving a session SHALL refuse, with nothing written, a `no_native_change` that holds only white space or a `<placeholder>`, and one held together with a native change, so an edit of the file by hand cannot allow the ungated move; the refusal SHALL name the session file and the field and say what to edit, the real reason in place of the value or the line removed, or one of the two fields removed. An empty `no_native_change` reads as none recorded. While it is recorded and no native change is, a stage move that SpecSync's configuration would otherwise refuse as `refused:no-native-change` SHALL be allowed and labelled `ungated:no-native-change-required`, so the session can advance to done and be archived with outcome `done` (REQ-history-006), its story keeping the reason; an open human gate that holds the stage SHALL still refuse the move (REQ-cli-030), and only a person closes it. Trace: FLOW-13, LIFE-3, DRIVE-3, DRIVE-24, DRIVE-25.

Acceptance Criteria
- A checkpoint saved by one process is read unchanged by `chough context` and `chough next` in another process; a front matter key with the wrong type is refused naming the file and the key, with nothing written.
- No second writable checkpoint store is introduced and no adapter is required; `.gitattributes` declares no `chough-session` driver and `chough checkpoint --merge` is not a command.
- With SpecSync configured, `checkpoint --native-change` for an ID SpecSync does not report, or after a failed or timed-out status read, exits non-zero with `refused:native-change-unknown` or the read failure and leaves the session file byte-identical even with other updates in the same call; a reply naming a different change refuses as `refused:native-change-mismatch` with the file byte-identical; a JSON reply naming no change ID, such as `[]` or `{}`, refuses as `refused:native-change-unknown` with the file byte-identical; a reported ID saves; without SpecSync any well-formed ID saves and a malformed one is refused.
- `chough checkpoint --pr 150` and `--pr` with a pull request URL each set the session's `pr`, which another process reads back; an empty value clears it; a value with a line break, or one holding a local path or a token, is refused with the session file byte-identical, or redacted under `--redact`; no Timeline entry is added.
- A session file edited by hand to hold `no_native_change: " "`, or to hold both `native_change` and `no_native_change`, is refused by `chough next`, `chough checkpoint` and `chough stage advance`, naming the file, the field and the edit, with every file byte-identical; `chough session list` still lists that session as not readable with that reason and `chough session shelve <id>`, `chough doctor` still runs, and a command given another open session is unaffected.

### REQUIREMENT REQ-cli-037

Active session checkpoint. The canonical checkpoint SHALL be the active session's `.chough/sessions/<id>/session.md`, named by the untracked pointer `.chough/local/active-session` or, with no pointer, the only open session or else the only open session that is not finished (REQ-history-006), and every command SHALL read and write that file. A command SHALL instead use the session that its `--session <id>` option names, or, without the option, the session the `CHOUGH_SESSION` environment variable names, each resolved by ID, alias or bare slug as `chough session use` resolves them, so each agent shell writes to its own session whatever the shared pointer says. A named session that is not open SHALL refuse the command, naming it, the option or the variable that named it, and `chough session list`, or, when no session is open at all, `chough session new <key>`, with nothing written, and the option and the variable SHALL never change the pointer. `chough init --session <key>` keeps its meaning, the first session's key, and `chough inbox add --session` already names its session; `chough session new` and `chough session use`, which set the pointer, ignore the option and the variable, and while either names an open session other than the one the command made active, the command SHALL say on standard error that it still names that session and that commands given it keep using that session. `chough session shelve <key>` SHALL take a key that is a session folder's name as that folder, and any other key as `chough session use` resolves it, by alias or bare slug, refusing one that names several sessions. A finished session, and a session folder whose story exists (REQ-history-006), SHALL NOT count toward several open sessions, and telling which sessions are finished SHALL need no native read (DRIVE-16). Chough SHALL refuse with nothing written when it cannot tell which session is active, and a command that needs a session when none is open SHALL refuse naming `chough session new <key>`. `chough init --objective <text>` SHALL create the first session as `chough session new` would, keyed by `--session <key>` or else by the objective's slug, and `chough init` without `--objective` SHALL create none. Only the active session is written, so this is not a second writable store (REQ-cli-007). Each command SHALL resolve the active session once and save only to that session, so a switch by another process partway through a command does not redirect its save; if that session is archived or removed meanwhile, the save SHALL refuse with nothing written. Trace: DRIVE-3, DRIVE-16, DRIVE-24.

Acceptance Criteria
- A stage move changes only the active session's `session.md`.
- No session, several open sessions without a pointer, and a pointer to a missing or archived session each refuse with nothing written, and the first names `chough session new <key>`.
- A `session use` by another process partway through a command leaves the newly active session's file unchanged, and the command's save lands in the session it resolved.
- With no pointer, an open session whose native change is archived on HEAD, and a session folder whose story exists, do not count toward several open sessions: the only other open session is active, with no native read.
- `chough init --objective <text>` creates one session named from the objective's slug, and `chough init` alone creates none.
- With two open sessions and the pointer on one, `chough evidence add --session <other>`, and the same command with `CHOUGH_SESSION=<other>`, record into the other session and leave the pointer unchanged, and `chough next --session <other>` shows that session.
- A `--session` or `CHOUGH_SESSION` naming an archived or unknown session refuses with every file unchanged.
- With `CHOUGH_SESSION` set in a project where no session is open, a command refuses naming `CHOUGH_SESSION` and `chough session new <key>` with every file unchanged, and with `--session` it names `--session`.
- `CHOUGH_SESSION=<a> chough session use <b>` makes `<b>` active and says on standard error that `CHOUGH_SESSION` still names `<a>`; with the variable unset it says nothing.
- `chough session shelve <alias>` and `chough session shelve <bare slug>` shelve the session `chough session use` would make active for that key, a key that is one session's folder name and another's alias shelves the folder of that name, and a session whose record cannot be read is still shelved by its folder name or bare slug.

### REQUIREMENT REQ-cli-057

SpecSync change steps through Chough. `chough change new <description> [--kind <kind>] [--spec <spec>]... [--path <path>]... [--no-spec-change --rationale <why>]` SHALL run `specsync change new <description>` with the same options and `--json`. `chough change answer <id> <question> <answer>` SHALL run `specsync change answer <id> <question> <answer> --json`. `chough change check <id>` SHALL run `specsync change check <id> --commit`, and `chough change check <id> --no-commit` SHALL run `specsync change check <id>` without it, the check the workflow's accept step runs first to materialize requirement text. `chough change status [<id>]` SHALL run `specsync change status [<id>] --json`. Each SHALL run in the project root given by `--root`, with the `specsync` that Chough's native reads use. Before SpecSync runs, each SHALL refuse with exit 1 an id, kind, spec, path or question argument that holds what the leak guard refuses in a written value or a control character (REQ-records-006), naming the argument and what it holds and not showing the value, so SpecSync's own error cannot show it; `--redact` SHALL NOT change this, since SpecSync, not Chough, would write the value. Each SHALL pass SpecSync's standard output, standard error and exit code through unchanged, and SHALL write nothing under `.chough/` except the untracked direct-write baseline of REQ-cli-060 under `.chough/local/`. `status` is a read and SHALL keep the native read bound (120 s unless `CHOUGH_NATIVE_TIMEOUT_SECONDS` sets it); past the bound it SHALL refuse with nothing recorded and name the retry with a longer bound. `new`, `answer` and `check` write, and SHALL never be stopped by that bound. Stopping Chough with SIGINT, SIGTERM or SIGHUP SHALL stop the SpecSync process it started (FLOW-14). When `specsync` cannot be started, each SHALL refuse with exit 1 and nothing run, naming the install command from the README's toolchain section and the same step run again.

Acceptance Criteria
- `chough change new --no-spec-change --rationale <why>` passes both options to SpecSync, and `--no-spec-change` without `--rationale` is refused before SpecSync runs, naming the command with `--rationale`.
- Each of `chough change new`, `answer`, `check` and `status` runs SpecSync with exactly the arguments above, in the `--root` directory, and its standard output, standard error and exit code match SpecSync's byte for byte, including a SpecSync refusal's.
- No `chough change` command changes a tracked file under `.chough/`; under `.chough/local/` it changes only its change's direct-write baseline (REQ-cli-060).
- `chough change check` completes after the native read bound has passed, while `chough change status` past the bound refuses with nothing recorded, and the retry it names succeeds.
- When `specsync` cannot be started, each command refuses with exit 1, naming the install command and the step to run again; with SpecSync installed, that step succeeds.
- A SIGTERM to `chough change check` stops the SpecSync process it started.
- `chough change check <id> --no-commit` runs `specsync change check <id>` without `--commit`, passes its output and exit code through, and the next stage move records no `direct-native-write` for what it wrote.
- `chough change new` with a credential sample as its `--path`, `--spec` or `--kind`, and `chough change status` with one as its id, each refuse before SpecSync runs, with and without `--redact`, name the argument and what it holds, and show no part of the sample; an id holding a control character is refused the same way.

### REQUIREMENT REQ-cli-059

Ship through Chough. `chough change ship <id> [--close-gate <gate> --decided-by <who> --words <words> --where <where> --recorded-by <agent>]` SHALL, before running anything and with nothing written, refuse unless the active session's native change is `<id>` and its stage is accept, and unless every open human gate of the active session is the one `--close-gate` names; another session's gates hold only that session's stages (REQ-cli-030). It SHALL also refuse before running anything, with nothing written and no native step run, when a commit between the change's recorded base commit and HEAD holds a change both open under `.specsync/changes/<id>/` and archived under `.specsync/archive/changes/<date>-<id>/`: SpecSync reads such a history as corrupt, so the archive's terminal evidence would not authenticate and the ship would stop halfway (#298). That check SHALL cover every commit in the range, however many. In a shallow clone that lacks the base commit, the ship SHALL refuse as `refused:history-unchecked`, naming `git fetch --unshallow`; in a complete clone whose recorded base commit is not an object, as after a squash merge removed it, there is no range to read, so the ship SHALL say so on standard error and go on; when Git cannot read a commit in the range, the ship SHALL refuse as `refused:history-unchecked`, naming that commit. Each step the command runs after the ship, the gate close and the move into done, SHALL act on the session the command itself resolved, named by `--session` or `CHOUGH_SESSION` or not (REQ-cli-037). The refusal SHALL name the commit and that change, and say to rebuild the branch from the default branch without that commit and then run `chough change check <id>` again. This check is interim, until SpecSync offers a validity preflight before the review (CorvidLabs/spec-sync#1082). The relay values SHALL be checked as `chough checkpoint --close-gate` checks them (REQ-cli-050). `--list <list> --gate <n>` MAY stand in for `--close-gate <gate>`: the gate SHALL be number `<n>` of that `chough gate list` list (REQ-cli-061), and its summary SHALL still have the listed digest, or the ship SHALL refuse before anything runs, naming `chough gate list`. The closed gate's relay SHALL then carry the summary digest and the list (REQ-history-014). Each refusal SHALL name the command that recovers. When the named gate drives review (REQ-cli-030) and the change has no current scoped review, it SHALL first record the review as the decided human with verdict `pass`, since a ship is run only on acceptance, as REQ-records-008 says, and SHALL stop with nothing more run or written when that review is refused. It SHALL then run `specsync change ship <id>` in the project root with no time bound, and pass SpecSync's standard output and standard error through unchanged. When SpecSync exits non-zero, it SHALL exit with that code and write nothing. When SpecSync succeeds, it SHALL close the named gate as `chough checkpoint --close-gate` would, a relayed claim, and then move the session to done as `chough stage advance --to done` would. After SpecSync's output it SHALL print by default a short text summary of the review, the ship, the gate close and the move into done, at most 12 lines, and SHALL print each step's full report under `--json`, so an agent loses nothing; when the summary is longer than 12 lines, its last line SHALL name how many lines were dropped and point at `--json` for the full report. When either step refuses after a successful ship, it SHALL exit 1, say that the change was shipped, and name each remaining command. Stopping Chough with SIGINT, SIGTERM or SIGHUP SHALL stop the SpecSync process it started (FLOW-14). The review step follows FLOW-23.

Acceptance Criteria
- With the review gate's relay, `chough change ship` runs `specsync change ship <id>` once, closes the gate with the four values as a relayed claim, and moves the session to done.
- A SpecSync refusal's standard output, standard error and exit code pass through, and nothing under `.chough/` changes.
- An open human gate without its relay, a wrong or incomplete relay, another change or a stage other than accept are each refused before SpecSync runs, with nothing written, and the command each names succeeds.
- When the move into done is refused after a successful ship, the exit is 1, the output says the change was shipped and names `chough stage advance --to done`, and that command then succeeds.
- `chough change ship` completes after the native read bound has passed.
- With `--list` and `--gate` for a listed review gate, the ship closes that gate with the summary digest and the list in its relay, and a summary changed since it was listed is refused before SpecSync runs, naming `chough gate list`.
- With a configured human and the review gate's relay, `chough change ship` runs `specsync change review` once as that human, with the relay's words, place and recording agent as `--words`, `--where` and `--recorded-by`, then `specsync change ship`; with no configured identity for `--decided-by` it refuses with `refused:human-identity-unknown` before SpecSync runs.
- The walkthrough and the skill's closeout run `chough change new`, `chough change check` and `chough change ship`, and record review through the human's gate decision.
- `chough change ship` prints SpecSync's output, then at most 12 lines naming the review, the ship, the gate close and the move into done; a summary longer than 12 lines ends with a line naming the dropped lines and `--json`; `chough change ship --json` prints every step's full report as before.
- With a commit between the change's base commit and HEAD that holds one change both open and archived, `chough change ship` refuses naming that commit and change, runs no SpecSync step and leaves every file unchanged.
- A history whose commit holding a change both open and archived is followed by 1,001 more commits is still refused as `refused:corrupt-history`, with nothing run; a shallow clone that lacks the recorded base commit is refused as `refused:history-unchecked`, naming `git fetch --unshallow`; and a complete clone whose recorded base commit is not an object ships, saying on standard error that its history from that base could not be checked.
- With the pointer on another session, `chough change ship <id> --session <s>` closes the gate and moves the stage in `<s>`, and the pointer's session file is byte-identical.
