# Keep evidence current across commits and SpecSync lifecycle bookkeeping, and verify bugs only by a pass observed after the failure

## Intent

Keep evidence current across commits and SpecSync lifecycle bookkeeping, and verify bugs only by a pass observed after the failure

## Affected Canonical Specs

- `cli`

## Acceptance Criteria

- Freshness compares content, not the commit: a new observation stays `current-observation` after committing only `.chough/` records, after an empty commit, and after committing working-tree edits that were already present when it ran; it becomes `stale-revision-or-inputs` when any fingerprinted file changes, whether tracked or untracked (source, tests, docs, `specs/`, `.specsync/` configuration, or a SpecSync change's deltas, requirements or other artifacts, before or after materialization) (BUG-0015, LIFE-2, LIFE-7, REQ-cli-004).
- Only lifecycle bookkeeping is excluded: the content digest leaves out `.chough/`, `target/`, and exactly these top-level files in each `.specsync/changes/<id>/` and `.specsync/archive/changes/<dated-id>/`: `state.json`, `approvals.json`, `verification.json`, `verification-attempts.json`, `review.json`, `review-attempts.json`, `finalization.json`, `accepted-state.json` and `lesson-bundle.md`, plus the value of the `state:` line in the front matter of `change.md` (a `state:` line in its body is still hashed). A `specsync change check --commit` that writes only these keeps observations current. Editing a delta, `requirements.md`, `testing.md`, `tasks.md` or any other artifact of an active change makes them stale before any `change check` (BUG-0016, LIFE-6, LIFE-7, REQ-cli-004).
- Finalizing moves the change directory into the archive and writes only files from that list, so it does not make observations stale: change artifacts are hashed under a key built from the change ID and their path inside the change, not from the directory location. A real artifact content change in the archive, or a file in the change or archive directory that is not on that list, makes them stale (BUG-0016, LIFE-6, REQ-cli-004).
- A tracked file deleted in the working tree is hashed as absent, so committing a deletion that was already present when the case ran keeps the observation current, and restoring the file makes it stale (BUG-0015, REQ-cli-004).
- Records keep their revision: each new observation still stores the HEAD revision, shown in status, next and the library index and used by `bug` regression-baseline ancestry, and evidence schema 2 gains an optional content digest that is validated as a SHA-256 digest when present. A record without the digest keeps the revision-bound comparison, so it stays stale after any new commit and never silently becomes current; a malformed digest is refused (LIFE-2, LIFE-7, REQ-cli-004, REQ-cli-017).
- Bug verification follows order: every bug verification label (`bug show`, `bug list`, `bug report` and the open backlog in `status` and `next`) reports `reproduced-and-later-passed`, and `bug update --status verified` is accepted, only when a present linked passed observation was observed strictly after the most recent present linked failed observation, compared by `observed_at_unix_seconds`. An older pass, or a pass in the same second as the failure, leaves the bug `reproduced` and refuses `verified` with a message naming the failing observation. A bug with no present linked failure reads `unverified` and refuses `verified` (BUG-0014, LIFE-5, REQ-cli-012).
- The accept order is documented in `references/accept.md` and `references/lifecycle.md` (canonical bundle, `.claude/skills` and `.agents/skills` copies, byte-identical), and in docs/lifecycle.md. The order is: when the delta adds or modifies requirements, run `change check` first to materialize them; `chough cases run`; record the gate with `chough checkpoint --awaiting-human`; commit the source together with `.chough/`; `specsync change check <id> --commit`; push and hosted CI; present the work; the human decision; `specsync change review`; `specsync change ship` or `finalize`; only then clear the gate and run `chough stage advance`. Between the check and finalize, nothing writes to `.chough/` and nothing is committed. The references say that until SpecSync offers an opt-in verification exclusion (the proposed upstream `verification_ignored_paths`), any Chough write in that window forces another `change check`. `references/bugs.md` says that `verified` needs a pass observed after the latest linked failure. `chough skill status` reports the main 2756dc2 copies of accept.md, lifecycle.md and bugs.md as known-outdated, not edited (FLOW-13, LIFE-6, REQ-cli-016).
- Contract and documentation agree: REQ-cli-004, REQ-cli-012 and REQ-cli-017 are reworded by MODIFIED delta items in the `### REQUIREMENT REQ-cli-NNN` form, applied to canonical headings that are exactly `### REQ-cli-NNN`; after approval and before `change check`, the REQ-cli-004 heading is normalized to `### REQ-cli-004` with its title moved into the body, exactly as requirements.md shows. Invariant 4, the docs/cli.md freshness table, docs/architecture.md, docs/walkthrough.md, docs/FRD.md (its REQ-cli-004 section and its excluded list), README.md, specs/cli/testing.md (the "stale ... by design" note), docs/lifecycle.md and the docs/NEXT_CHANGE.md status say that the revision is recorded but not compared; docs/exercises/cold-start.md gains a dated note that its stale reading came from the earlier rule. docs/DECISIONS.md records the human's decision on this scope as a new decision that supersedes D-016. The `stale-revision-or-inputs` label keeps its name for JSON compatibility, and specs/cli/context.md gains the lesson from CorvidLabs/raven#644 (LIFE-7, REQ-cli-004).
- No regression: before the fix, new cases for BUG-0014, BUG-0015 and BUG-0016 each record a failing reproduction linked to its bug; after it they pass, and those bugs are verified by later passes. Existing tests pass, and an existing expectation changes only where testing.md names it as following from these criteria. The full suite and `fledge lanes run verify` pass, and hosted CI passes on Ubuntu, macOS and Windows (LIFE-5, LIFE-7).
