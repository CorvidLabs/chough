## MODIFIED

### REQUIREMENT REQ-cli-067

Readiness before approval. `chough change ready <id>` SHALL read the active change `<id>` and SHALL leave every tracked file as it found it. It SHALL print one report and SHALL exit 0 when that report has no finding and 1 when it has any. An unknown change SHALL exit 1 and name `chough change status`. Each finding SHALL name one exact command that fixes it, with the real change id and paths filled in. Trace: DRIVE-29.

The report SHALL name a finding for each of these, and for nothing else:

- Approval checks. Each check that `specsync change approve <id> --dry-run --json` reports as refused, in SpecSync's own message, so the report names whatever the definition approval would refuse, a missing or extra delta among it, without copying SpecSync's rules (#406, #307). The fix is the `fix` SpecSync gives with it, shown as given and never run, any placeholder in it left for the person to fill; without one, the fix is `chough change ready <id>`, run again once the message's problem is fixed. When `specsync` cannot be started, or prints no dry-run document, as a SpecSync before 6.4.0 does, the finding says the approval could not be checked and names `cargo install --locked specsync@6.4.0`.
- Stale canonical text. When the latest definition approval recorded bases, each `## MODIFIED` or `## REMOVED` item whose delta body is unchanged since that approval and whose canonical block now differs from the recorded base, unless the approved body already carries every edit the current text made to that base. The finding names the module and the requirement or section. The fix is `rewrite .specsync/changes/<id>/deltas/<module>.md` and then `chough change ready <id>`.
- Undocumented exports. For each affected spec, each undocumented export that `specsync check --spec <module> --format json` reports from a file an affected path covers. The fix is `document <symbol> in specs/<module>/<module>.spec.md`. When `specsync` cannot be started, the finding names `cargo install --locked specsync@6.4.0`.
- Cross-module cases. In each `.chough/cases` file that changed since the change's base or that an affected path covers, a case that links a requirement owned by another module. The fix is `move <case> to .chough/cases/<owner>.<topic>.cases.toml`.
- Paths outside the declaration. Each file that differs from the change's `base_commit` and is the change's own work, that no affected path covers, other than a path under `verification_ignored_paths` or under `.specsync/changes/<id>/`, SpecSync's own untracked `.specsync/change.lock` and `.specsync/workflow-v2-baseline.json`, and a path under another active change's own `.specsync/changes/<other>/` folder or covered by one of its affected paths, other than one that covers the whole project, since that work is the other change's (#406). A file is the change's own work when a commit on the branch's first-parent line since `base_commit` changed it, counting for a merge commit only the files its result changes against every parent, or when it is unstaged, staged, or untracked and not ignored by Git; a file that only a merge from another branch brought in is not. Nor is a committed file whose content at HEAD is the default branch's, at the default branch's tip or at HEAD's merge base with it, so the files a rebase onto the default branch or a squash merge of it brought in are not named. The default branch is the remote-tracking branch `refs/remotes/origin/HEAD` names, unless it names no existing ref or names the branch HEAD is on, by the same name or as its upstream; then `refs/remotes/origin/main`; and a local `main` only when the repository has no remote. While HEAD is on the default branch, or the default branch's tip is HEAD, or there is no default branch, no file is left out this way and the files are counted from `base_commit` as before, so work done on the default branch itself is still named. When HEAD's merge base with the default branch cannot be computed, as in a shallow clone, only the tip is compared, and the report SHALL say so on standard error without printing Git's own error. When `base_commit` is not in the repository, as after a squash merge removed it, the report SHALL say so, naming it, and SHALL count the change's work from HEAD's merge base with the default branch; when there is no default branch or no such merge base, it SHALL name one finding that the changed files could not be listed and why, with the fix `git fetch --unshallow` in a shallow clone and `chough change status` otherwise, and SHALL never print Git's own error or report that nothing is missing. While the change is a draft, the fix is one `chough change answer <id> affected_paths "<the full list>"`. Otherwise the fix is `specsync change send-back <id> --actor <name> --reason "<the paths>"`.
- Interview and unfinished artifacts. Each interview question SpecSync still asks. The fix is `chough change answer <id> <question> "<answer>"`. Each selected artifact whose body is empty or only a TODO placeholder, and a plan that is missing approach, out of scope, steps, risks, or constraints consulted. The fix names that artifact's path.

Acceptance Criteria
- A draft with an unanswered question and a TODO artifact exits 1 and names the fix for each, a missing and an extra delta are named in the message of SpecSync's dry run, and the same command exits 0 once they are fixed, having changed no file.
- A delta approved against a requirement, then left unchanged while that requirement's canonical text changes, is named, and a delta rewritten onto the new text is not.
- An undocumented export in a declared file is named as `specsync check --spec` names it, and an export in a file the change does not declare is not.
- A changed case that links another module's requirement is named with the owning module, and a case that links only its own module is not.
- A changed file outside the declared paths is named, a file under a declared prefix is not, and a file under `verification_ignored_paths` is not. On a draft the fix is `chough change answer` with the full path list.
- A file outside the declared paths that a merge from another branch brought in is not named, and a file outside them that the merge's own resolution changed is named.
- An unknown change id exits 1 and names `chough change status`.
- On a branch rebased onto the default branch after the change recorded its base, a file only the default branch's commits changed is not named, and a file outside the declared paths that the change's own commits changed is named.
- On a branch that squash-merged the default branch, a file whose content at HEAD is the default branch's is not named, and a file the change changed outside the declared paths is named.
- With a `base_commit` the repository does not have, the report says so, naming it, prints no `fatal:` line, and still names a file outside the declared paths that the change's own commits changed.
- With HEAD on the default branch, or the default branch's tip at HEAD, or `refs/remotes/origin/HEAD` naming HEAD's own branch, a file outside the declared paths that the change changed is still named.
- With a `base_commit` the repository does not have and no default branch, the report names one finding that the changed files could not be listed, prints no `fatal:` line, and does not say that nothing is missing.
- With SpecSync's dry run refusing a check, as it does for a delta with no SHALL, a declared spec with no spec file, an affected `src/` path no declared module owns, or `no_spec_change` with `public_contract` answered yes, the report names the refusal in SpecSync's words, with SpecSync's `fix` when it gives one, and exits 1; with the dry run accepting, it adds no finding of its own (#406, #307).
- With a `specsync` that prints no dry-run document, the report names the approval as unchecked with `cargo install --locked specsync@6.4.0`, exits 1, and never says that nothing is missing.
- In a project that never ran SpecSync's adoption, untracked `.specsync/change.lock` and `.specsync/workflow-v2-baseline.json` are not named outside the declared paths, while another untracked file under `.specsync/` still is.
- With two active changes on one branch, a file only the other change declares is not named for this one, and a file neither declares still is.
- With another active change declaring `.`, a file outside this change's paths is still named.
- In a project with no `.specsync/hashes.json`, no SpecSync command that `chough change ready` runs finds one.
