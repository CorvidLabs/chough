## MODIFIED

### REQUIREMENT REQ-cli-007

Canonical checkpoint. The helper SHALL keep one canonical checkpoint per open session: the front matter of the active session's `session.md` (REQ-records-004, REQ-cli-037), holding the objective, intent scope, modules, current stage with its status, iteration and side-stage callers, the native change identity, the pull request, referenced criteria, requirements, cases, design sources and files, observation and bug references, blockers, awaiting-human gates, run consents and the next action, with decisions, completed work and open questions in the story sections of the same file. No other writable checkpoint store SHALL exist and no adapter such as APS SHALL be required. Every read SHALL validate the front matter's keys and value types and SHALL refuse a malformed one naming the file, the key and the rule (REQ-records-001). `chough checkpoint --merge` and the `chough-session` merge driver are removed, because each session has its own folder and parallel branches never write one checkpoint (DRIVE-24). When SpecSync is configured, `chough checkpoint --native-change <id>` SHALL read `specsync change status <id>` before it applies any update, and SHALL refuse as `refused:native-change-unknown`, naming the ID and that status command, when SpecSync does not report the change; a failed or timed-out read SHALL also refuse, and a reply whose `summary.id` or `change.id` names a different change SHALL refuse as `refused:native-change-mismatch`, naming both IDs. A JSON reply that names neither `summary.id` nor `change.id` SHALL refuse as `refused:native-change-unknown`, since it does not identify the requested change. Every such refusal SHALL leave the session file byte-identical, including the other updates given in the same call. An ID SpecSync reports, archived or open, SHALL be saved as before. Without a SpecSync configuration only the existing ID format check SHALL apply, with no native read. `chough checkpoint --no-native-change <reason>` SHALL record, as `no_native_change` in the session's front matter, that the session's work needs no native change and why; it SHALL refuse a blank reason, SHALL refuse with nothing saved while the session records a native change, naming it, and recording a native change SHALL remove it. While it is recorded and no native change is, a stage move that SpecSync's configuration would otherwise refuse as `refused:no-native-change` SHALL be allowed and labelled `ungated:no-native-change-required`, so the session can advance to done and be archived with outcome `done` (REQ-history-006), its story keeping the reason; an open human gate that holds the stage SHALL still refuse the move (REQ-cli-030), and only a person closes it. Trace: FLOW-13, LIFE-3, DRIVE-3, DRIVE-24, DRIVE-25.

Acceptance Criteria
- A checkpoint saved by one process is read unchanged by `chough context` and `chough next` in another process; a front matter key with the wrong type is refused naming the file and the key, with nothing written.
- No second writable checkpoint store is introduced and no adapter is required; `.gitattributes` declares no `chough-session` driver and `chough checkpoint --merge` is not a command.
- With SpecSync configured, `checkpoint --native-change` for an ID SpecSync does not report, or after a failed or timed-out status read, exits non-zero with `refused:native-change-unknown` or the read failure and leaves the session file byte-identical even with other updates in the same call; a reply naming a different change refuses as `refused:native-change-mismatch` with the file byte-identical; a JSON reply naming no change ID, such as `[]` or `{}`, refuses as `refused:native-change-unknown` with the file byte-identical; a reported ID saves; without SpecSync any well-formed ID saves and a malformed one is refused.
