# Fresh-agent handoff from existing records: chough next shows recent decisions, the last failure and a lessons pointer, names a new cycle after the native change is archived, and the skill labels lesson certainty and closes out inside the open change

## Intent

Fresh-agent handoff from existing records: chough next shows recent decisions, the last failure and a lessons pointer, names a new cycle after the native change is archived, and the skill labels lesson certainty and closes out inside the open change

## Affected Canonical Specs

- `cli`

## Acceptance Criteria

- Archived-not-done guidance: when the checkpoint stage is intent, design, plan, build, test or accept, active, with no awaiting-human gate and (at test or accept) no open acceptance-blocking bug, and the recorded native change is archived with authenticated terminal evidence, `chough next` (text and `--json`) and `chough status` no longer say `Continue <stage>` and no longer give the build gate refusal as the action. The next valid action says that native change <id> is archived while the checkpoint is at <stage>, then names the new cycle in done_action's wording: `Start a new cycle: chough stage reset --to intent --reason "<why>" (or --to plan when the approved intent already covers the new work), then specsync change new "<outcome>" --spec <module> --path <path>, then chough checkpoint --native-change <id> --next-action "<next step>".` At accept it first names `chough stage advance` to record done, the documented close after finalize, and its command is that advance; at the other stages its command is the reset with `--reason`. A native next action, when status reports one, is shown as the thing to check first. Paused stages, awaiting-human gates, blocking bugs at test or accept, stage done, release, side stages and an archive whose terminal evidence does not authenticate keep today's behavior. Tests in tests/next.rs drive plan, test and accept fixtures with an archived stub change, check the text, JSON and status agree, and run the suggested reset with its placeholders filled, which succeeds (FLOW-13, LIFE-3, REQ-cli-021).
- Decisions block: `chough next` shows the total number of checkpoint decisions and up to the 5 most recent (the last 5 entries of `decisions`, newest first). An entry that begins with `decided:`, `rejected:` or `failed:` is shown with that kind; when its text contains ` because `, the part after the last ` because ` is shown as its reason and the part before it as its text. Any other entry is shown whole with no kind and no reason (the latest-N fallback). The checkpoint schema and the stored strings are unchanged. Each text and reason is cut to at most 512 bytes with the existing visible cut marker. JSON carries `decisions: {total, items: [{kind, text, reason}]}` with null for an absent kind or reason. A test with 7 decisions mixing the three prefixes, an unprefixed entry, a dated entry and a 4 KiB entry shows exactly the last 5 in order, with the stated kinds, reasons and cut (LIFE-3, FLOW-13, REQ-cli-021).
- Last failure block: `chough next` names the observation in `.chough/evidence/` whose outcome is failed (the Outcome in src/evidence.rs) with the greatest `observed_at_unix_seconds`, ties broken by the greater observation ID, with its ID, observed time and summary cut to 512 bytes, plus every bug that links it (by its observations, note observations or regression baseline) with that bug's ID and status, at most 3 with their total; with no failed observation it says none. The choice uses recorded times only, never file modification times or directory order. JSON carries `last_failure: {id, observed_at_unix_seconds, summary, bugs: {total, items: [{id, status}]}}` or null. A test seeds failed observations whose recorded times disagree with their file names and modification times: the latest recorded one is shown, its linked bug's status is shown, and an unlinked failure shows no bugs (LIFE-3, FLOW-13, REQ-cli-021).
- Lessons pointer: for each module in the checkpoint, `chough next` names the lesson source SpecSync briefs, `specs/<module>/<module>.3md` when present, otherwise `specs/<module>/context.md` with the line number of its `## Lessons` heading, or says that the file has no Lessons section or is missing. It reads and prints no lesson text. It counts the `.specsync/archive/changes/*/lesson-bundle.md` files and lists up to 5 of their paths, newest first by archive directory name. It records no folded or unfolded state and adds no ledger, index or store. JSON carries `lessons: {sources: [{module, path, section_line}], archived_bundles: {total, items}}`. Tests cover a context.md with a Lessons section, one without, a present .3md and 7 archived bundles (LIFE-1, FLOW-12, REQ-cli-021, REQ-cli-002).
- Bounded and deterministic: the new blocks count against the existing 16384-byte cap of each form; when the view would exceed it, decision and archived-bundle entries are dropped like other list entries, `truncated` becomes true and every total stays correct. A fixture with 50 decisions of 4 KiB each, 200 observations of which 100 failed, 40 bugs linking the latest failure, 40 archived bundles, and the existing 500 referenced stale observations, 40 awaiting-human gates and 40 blockers of 4 KiB each keeps both forms within 16384 bytes with correct totals. Two runs over the same records, and a run after every record's file modification time is changed, give byte-identical text and byte-identical JSON. `chough next` still makes at most one native status read, the view keeps schema_version 1 with the new fields added, and on this repository the pull request reports both forms' byte counts (LIFE-3, REQ-cli-021).
- Skill guidance: in skills/chough-workflow, references/accept.md (Compounding) says each lesson carries a certainty label, `observation`, `hypothesis` or `verified`, with its source (an observation, bug or commit) and its limits, and that a project decision (a checkpoint decision, a docs/DECISIONS.md entry or an approved contract) always outranks a lesson, which never changes the decision. references/checkpoint.md documents the `decided:`, `rejected:` and `failed:` prefixes with a `because` reason as a convention read best-effort, and what the new next blocks show. references/bugs.md says a failing check that is fixed in the same pull request still gets a bug record or a lesson entry. references/librarian.md describes closeout as one quiet skill pass inside the open native change, before `specsync change check <id> --commit` and finalize: it writes supported lessons from the change into the module lesson source with their labels, checks that new decisions carry a reason and that verified bugs link their observations, adds one `completed` checkpoint entry, and ends with one closeout summary of at most 12 lines; it never edits specs after archive (a lesson found later goes into a new native change), it works with the librarian preference off (REQ-cli-015), and it writes a library brief only when the librarian is on. references/lifecycle.md and references/accept.md replace "the proposed upstream `verification_ignored_paths`" with wording that SpecSync 6.1.2 ships it, that Chough's own repository has not adopted it, and why (entries are directory prefixes, so covering `.chough/session.json` would also hide `.chough/cases/`). No other file gets the housekeeping fix in this change. The agent-assisted case reads each statement at the implementation tip (FLOW-12, LIFE-1, REQ-cli-002, REQ-cli-015).
- Installed copies stay current: .agents/skills/chough-workflow and .claude/skills/chough-workflow are byte-identical to the canonical bundle; KNOWN_PREVIOUS in src/skill.rs gains the fb6e487 digest of every bundle file this change edits; tests/fixtures/skill-fb6e487/ holds those fb6e487 bytes and a test in tests/package.rs shows an unedited fb6e487 copy reads known-outdated and is updated while an edited copy stays edited; no bundle file gains U+2013 or U+2014 (REQ-cli-016, REQ-cli-019).
- Contract and docs: the delta MODIFIES REQ-cli-021 (the three handoff blocks, the archived-not-done action and determinism) and REQ-cli-002 (the lesson source pointer, certainty labels in the native source, and a project decision outranking a lesson) only. No requirement is added or removed; REQ-cli-012, bug IDs and the bug schema are untouched; no hi/ file is edited; the checkpoint schema stays 2; no new store, ledger, record kind, command, model client or integration is added. docs/cli.md documents the new blocks, the prefix convention and the archived-not-done action; CHANGELOG.md gets an Unreleased entry; docs/ROADMAP.md changes only to list this slice. Cases TC-cli-0126 to TC-cli-0133 are added to .chough/cases/cli.cases.toml after the scoped `specsync change check` materializes the delta, as status active, each with an observation at the implementation tip; TC-cli-0125 and BUG-0026 are not used.
- Cold-start proof, protocol fixed before implementation: before any implementation commit, docs/exercises/handoff-cold-start/ holds a seed script that builds a disposable Git repository from static files, and a written pass/fail rubric (rubric.md). The seeded repository has a goal; two human decisions in the checkpoint, one of them `rejected: <approach> because <reason>`; one failed experiment that mixed a real defect with a case binding error, recorded as a failed observation with a linked bug; a verified fix with a `verified` lesson in its specs/<module>/context.md Lessons section; and an unfinished next task. The SHA-256 digests of the seed script and the rubric are recorded as one Chough observation with both files as artifacts before implementation; if either file changes afterwards, every run made with the old pair is void and the new pair is recorded as a new observation before any new run. Mandatory baseline: a fresh agent process on a host other than the author's, Kimi Code CLI 0.41.0 or Codex CLI 0.153.4, started in the seeded repository with the binary and skill from main at fb6e487, given only the repository, the installed skill and the prompt `Resume this project.`. Change run: the same host, model and prompt, with the binary and skill from the implementation tip. Real-repository run: the same host and prompt once on this repository at the implementation tip. Each run's transcript and command log are kept as hashed observation artifacts with the host, model and version. A run passes the rubric only if, before its first edit, its transcript states the goal, cites both decisions and the reason for the rejection, names the failure, its bug status and the lesson, and starts the correct next task, and its command log shows it neither repeats the failed experiment nor proposes the rejected approach. These do not count: the same session or a fresh command process of the authoring agent; any hint beyond the fixed prompt; recovery that needed `git log`, `gh` or docs/ROADMAP.md; simulated actors; a grader feeding answers. 0xLeif grades every run against the frozen rubric and his grade is recorded as his statement, not as an approval. This criterion holds when he grades the change run a pass; the baseline and real-repository results are reported beside it whatever they are, and if the baseline also passes the pull request says the runs show no difference from main (LIFE-3, FLOW-13, LIFE-1).
- Verification: the full suite and `fledge lanes run verify` (fmt, lint, test, intent, `specsync check --strict --require-coverage 100`, `specsync change audit`, `chough cases check`, exercise, build) pass locally with hi 0.8.0, fledge 1.8.0 and specsync 6.1.2, and CI passes on Ubuntu, macOS, Windows and MSRV; results are reported per platform and nothing unobserved is claimed.
