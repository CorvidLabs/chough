## MODIFIED

### REQUIREMENT REQ-cli-061

Gate lists. `chough gate list [--json]` SHALL number every open human gate of every open session in the project from 1, with the stage it holds and the native step it drives (REQ-cli-030). It SHALL give each a one-screen summary of at most 24 lines and 4,096 bytes, with:
- what changed: the files, insertions and deletions since the change's base, leaving out `.chough/`, the knowledge directory and SpecSync lifecycle bookkeeping, and naming the five files with the most changed lines among the rest (#190). At a gate that drives approval, the change's own definition, the Markdown files under `.specsync/changes/<id>/` (its `change.md`, deltas, plan and other artifacts), is what the human approves, so the summary SHALL count those files and name them first, never leaving them out as bookkeeping. The base is the change's own `base_commit` (from its `state.json`), so an earlier change on the same branch is not counted again. The base is instead the merge base of HEAD with the default branch (`origin/HEAD`, else `main`) in two cases: when that merge base is not an ancestor of the `base_commit`, meaning default-branch work was merged or rebased in after the change began (#190), and when the change records no `base_commit`. A merge base that is HEAD itself, as on the default branch, is not used. With no usable base, the summary says the base is unknown;
- the tests: how many cases passed, failed and were not run, by the latest observation of each case that links a requirement the change's deltas add or modify, or that the session's observations name, with the failing case IDs;
- the risks: the first 8 lines of the change's `plan.md` section "Risks", or "none recorded";
- a diff link: the GitHub compare URL from the base to HEAD when `origin` is a GitHub remote, otherwise `git diff <base>..<HEAD>`.

Each summary's digest SHALL be the SHA-256 of its text. The list SHALL be saved as `.chough/local/gate-lists/<list>.json`, where `<list>` is the first 12 hex digits of the SHA-256 of the list. Listing SHALL make no native read and write no tracked file.

`chough gate record <list> --gates <n>[,<n>...] --decided-by <who> --words <words> --where <where> --recorded-by <agent>` SHALL close each named gate as `chough checkpoint --close-gate` would with the four values (REQ-cli-050), and its relay SHALL carry that gate's `summary_digest` and the `list` (REQ-history-014). It SHALL close all the named gates or none. Before writing anything, it SHALL refuse:
- an unknown list, a number not on it, a listed gate that is no longer open, or a gate whose summary's digest has changed, each naming `chough gate list`;
- a gate whose change's `state.json` state is `verifying`, naming `chough change ship <id> --list <list> --gate <n>` with the relay;
- more than one named gate that drives a native step, naming the gates to record one at a time.

A named gate that drives a native step SHALL run it as the decided human (REQ-records-008) before any gate is closed.

Acceptance Criteria
- `gate list` numbers each open gate with a summary naming what changed, the tests, the risks and a diff link, at most 24 lines, and the SHA-256 digest of its text; the list is saved under `.chough/local/gate-lists/` and no tracked file changes.
- One `gate record` reply naming two listed gates closes both, each relay keeping the same words and its own summary digest; a gate left off the reply stays open.
- An unknown list, a number not listed, a gate no longer open and a summary changed since listing are each refused with nothing written, and listing again then recording succeeds.
- A gate whose change is verifying is refused, naming `chough change ship` with `--list` and `--gate`, which then ships and closes it with its digest.
- Two named gates that both drive a native step are refused with nothing run or written; one such gate with gates that drive nothing runs its step once and closes all of them.
- #190: with a one-line product edit, 300 changed records under `.chough/` and `knowledge/`, and 200 files merged from main after the base, the summary counts one file and names it.
- For a second native change on one branch, the summary's what changed counts only that change's own files since its `base_commit`, not the earlier change's; with default-branch work merged in after it began, it counts from the merge base, as #190's criterion requires.
- At a scope gate, the summary's what changed counts and names the change's deltas and plan under `.specsync/changes/<id>/` first, while its `state.json` and `approvals.json` stay left out.

### REQUIREMENT REQ-cli-012

Local bug backlog. The helper SHALL keep each bug as one Markdown record, `.chough/bugs/<id>.md` (REQ-records-001), whose front matter gives `kind: bug`, `id`, `aliases`, `title`, `status`, `classification`, `scope`, `impact`, `criteria`, `requirements`, `cases`, `evidence` (the linked evidence IDs), `receipts` (the receipt fields of REQ-history-006 for linked evidence no longer in an open session), `regression_baseline`, `fixture`, `environment`, `revision`, `found_by` (the actor, REQ-records-007), `fixed_in`, `duplicate_of`, `related`, `created` and `updated`, where `regression_baseline`, `fixture`, `fixed_in` and `duplicate_of` are written only when set and a missing one reads as empty, and whose body gives `# <title>` and the paragraphs What happened (the symptom and actual behavior), Steps (the trigger, labelled `Trigger:`, then each step), Expected, Why it matters and Fix (`Not fixed yet.` until `chough bug update --fix <text>` sets it, each set also logged; marking a bug verified while its Fix still says `Not fixed yet.` SHALL replace that with a line naming the passing observation and its revision), then `## Log`, an append-only list with one dated entry per report, note, evidence link and status change. It SHALL list open bugs for a fresh session and SHALL search existing records by symptom, trigger and affected IDs before a new record is added. A bug SHALL remain unverified until a failed observation is linked, and a regression classification SHALL require a passed observation at an ancestor revision. A bug SHALL read as reproduced and later passed, and SHALL accept the verified status, only when a present linked passed observation was observed strictly after its most recent present linked failed observation; a receipt counts as present, and an observation shown as removed (REQ-records-009) does not. Additional evidence SHALL be appended to the Log, never overwriting anything. A bug in another tool's behaviour MAY be closed as `fixed-upstream` with `bug update --status fixed-upstream --note <text>`, the note naming the upstream fix and who checked it where; it is a closed status, as `verified`, `duplicate` and `wont-fix` are, needs no Chough observation, and SHALL never read as verified by Chough. The helper SHALL render a report candidate and SHALL NOT publish it. Every new bug SHALL be named by REQ-records-003 from its title, the same for manual `bug add` and automatic failure capture, and written by create-new; an update SHALL NOT rename the record, even when its title has changed. Every `BUG-NNNN` and `BUG-<slug>-<hex>` ID from 0.5.x SHALL resolve as an alias, and duplicate and related links SHALL resolve in either direction across aliases and new names. Documentation SHALL state that Chough 0.5.x cannot read 0.6.0 bug records. Trace: FLOW-8, LIFE-5, LIFE-8, DRIVE-25, DRIVE-27.

Acceptance Criteria
- A sample failure becomes a reproduced and classified bug; a second report of the same symptom is found by search and its evidence is appended to the Log.
- A regression classification without a passed observation at an ancestor revision is refused.
- An out-of-scope bug stays in the open backlog without changing the checkpoint scope.
- Rendering a report candidate prints Markdown and performs no network action.
- A pass observed before, or in the same second as, the latest linked failure leaves the bug reproduced and the verified status is refused; a bug with no linked failure cannot be marked verified.
- `--classification blocking` is refused with a hint to use `--scope`, and `--scope product-defect` with a hint to use `--classification`.
- Manual `bug add` and automatic failure capture both name the bug `<date>-<title slug>`, and changing a stored title and then updating its status or evidence leaves the name unchanged.
- Each update appends one Log entry and leaves every earlier Log line, and every body paragraph a person wrote, byte-identical.
- A migrated bug answers to its `BUG-NNNN` alias in list, search, show, update and report, and duplicate and related links resolve from alias to new name and back.
- After the session holding a bug's linked evidence is archived, the bug resolves that evidence to the story's receipt and its verified state is unchanged.
- The CLI documentation says Chough 0.5.x cannot read 0.6.0 bug records.
- `bug update --status fixed-upstream` without a note is refused; with one it closes the bug, `bug list` shows it closed as fixed upstream, and nothing reports it verified.
- A new bug's Steps start with `Trigger:` and the trigger; `bug update --fix <text>` sets the Fix paragraph and logs it; a bug marked verified with no Fix set says which observation passed at which revision instead of `Not fixed yet.`
