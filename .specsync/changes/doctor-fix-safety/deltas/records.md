### REQUIREMENT REQ-records-001

Record files. Every record Chough writes, a session, an archived session story, an evidence entry, a bug, an inbox entry, a journal post and a migration receipt, SHALL be one UTF-8 Markdown file that starts with YAML front matter between two `---` lines, and that file SHALL be the record's only source of truth: no JSON or other twin SHALL be written beside it, and no index, cache or generated note SHALL be read in its place. The front matter SHALL carry the IDs and fields agents parse; the body SHALL carry the record for a human reader. Front matter SHALL use a strict subset of YAML that Chough reads and writes without a new dependency: `key: value` scalars, plain or double-quoted with `\"`, `\\` and `\n` escapes; flow lists `[a, b]`; block lists of scalars; and block lists of flat maps of scalars. Chough SHALL refuse front matter outside that subset, a duplicate key or a missing closing `---`, naming the file, the line and the rule, and SHALL write nothing in that command. A record's body SHALL NOT hold a Git conflict marker: a line that starts with `<<<<<<<` or `>>>>>>>`, or a line of `=======` between such lines (a `=======` line outside them, as a Markdown heading underline, is not one); a line inside a closed fenced code block, as CommonMark reads one, quoting an example or tool output, is not one, but a fence that never closes hides nothing after it, and no fence hides a conflict in a section Chough writes itself, a session's `## Timeline` or an archived story's `## Receipts` (#339). A real conflict Git leaves inside such a fence cannot be told from a quoted one, so no write SHALL be refused for it, and `chough doctor` SHALL only warn of each marker line there (REQ-cli-055). A lone `=======` outside a conflict may be left by a half-resolved conflict, but a heading underline may be followed directly by text, so no write SHALL be refused for it, and `chough doctor` SHALL only warn of it (REQ-cli-055). Chough SHALL refuse a write whose body would hold one as `refused:conflict-markers`, naming the file, the line and the marker, with every file unchanged, and `chough doctor` SHALL report each committed record whose front matter or body holds one as a `conflict_markers` finding naming the file, the line and the marker, which has no fix (#374). Reading SHALL be tolerant: an unknown front matter key SHALL be kept byte for byte, in place, when Chough rewrites the front matter, and SHALL be ignored otherwise; a missing optional key SHALL take its documented default; CRLF line endings SHALL be read as LF. Chough SHALL own only the front matter and the sections it appends to, and SHALL keep every other body byte a person or agent wrote: a write SHALL replace the front matter, append list items to the end of a named section, or create a missing named section at the end of the body, and SHALL do nothing else to an existing body. Files SHALL be written with LF line endings by an atomic replace under the writer lock of REQ-cli-040, or by create-new for a new record. A record SHALL be at most 65,536 bytes, except a session record, an archived session story and a migration receipt, which SHALL be at most 1,048,576, 1,048,576 and 4,194,304 bytes; a record over its bound SHALL be refused with the bound named and every file byte-identical. When a 0.5.x record would migrate into a record that holds a marker, the preview SHALL say that the apply refuses and SHALL NOT offer the apply command, and `chough migrate --apply` SHALL refuse with nothing written, each naming the 0.5.x file to resolve, the record it would become, the line and the marker. Trace: DRIVE-25, DRIVE-26, DRIVE-28, KNOW-32, LIFE-3.

Acceptance Criteria
- Every record kind written by a fixture cycle (session, archived story, evidence, bug, inbox entry, journal post, migration receipt) starts with front matter that the reader parses, and no `.json` file is written under `.chough/` except the local caches of REQ-history-007 and `.chough/preferences.json`.
- A person's edit to a session's Goal paragraph, to a bug's Steps and to an evidence entry's body survives a following stage move, decision, evidence add and bug update byte for byte.
- An unknown front matter key added by hand is kept byte for byte after Chough rewrites that front matter, and a missing optional key reads as its default.
- Front matter with a nested map, an anchor, a duplicate key or no closing line is refused with the file, line and rule named, and nothing is written.
- A CRLF copy of a record reads the same as the LF original.
- A record one byte over its bound is refused naming the bound, with every file unchanged.
- A record write whose body holds a `<<<<<<<`, `=======` or `>>>>>>>` conflict line is refused as `refused:conflict-markers` naming the file, the line and the marker, with every file unchanged; a body with a `=======` heading underline and no conflict is written.
- With a committed record whose body holds a conflict, `chough doctor` reports a `conflict_markers` finding for each marker line naming the file, the line and the marker, exits 1, and reports none for a tracked file that is not a record.
- A conflict quoted inside a fenced code block, with backtick or tilde fences, is not a marker and the record saves; a lone `=======` with text after it is not refused either.
- A conflict after a code fence that never closes, or after a backtick line whose tag holds a backtick, is a marker and the write is refused.
- A conflict inside an archived story's `## Timeline` or fenced `## Receipts` block is a marker, inside a fence or not.
- A Git conflict left inside a code fence of a session's Goal is not refused on the next write.
- A 0.5.x inbox entry whose text holds a conflict makes the migration preview say the apply refuses, without offering the apply command, and the apply refuse, each naming that 0.5.x file first.
- A committed record whose front matter holds a conflict, as two branches that each set `--objective` leave after a merge, gives a `conflict_markers` finding for each of its marker lines (#374).

### REQUIREMENT REQ-records-014

Chough's records stay out of SpecSync's verification. The folders Chough writes while work is in progress, `.chough/sessions/`, `.chough/archive/` and `.chough/bugs/`, SHALL hold only Chough's records: no case definition, preference, reading guide or other input that a change's verification needs SHALL be written under them, and `.chough/cases/`, `.chough/preferences.json`, `.chough/README.md` and `knowledge/` SHALL stay outside them. These three prefixes are what a project lists in SpecSync's documented exclusion, `verification_ignored_paths` in `.specsync/sdd.json` (SpecSync 6.1.2 and later), so that a Chough record written after `specsync change check --commit`, whether left untracked or committed, leaves the recorded verification current, in the author's tree and in a reviewer's clean checkout alike; `.chough/local/` is already Git-ignored and never part of it. Chough SHALL read that policy and SHALL never write it: `chough doctor` SHALL report `records_in_verification` (REQ-history-012) while `.specsync/sdd.json` exists and its list lacks any of the three prefixes, naming the missing entries, the SpecSync version that supports them and that adding them is an ordinary reviewed change to `.specsync/sdd.json`; `chough init` SHALL print the same advice; and the migration plan and receipt SHALL list it as a follow-up (REQ-records-009). The spec files read for this advice SHALL be found without following a symbolic link, to a file or to a folder, so a link out of the project cannot make outside code count and a link cycle cannot hang `chough doctor` or `chough init`; the walk SHALL read at most 4,096 entries and 32 folders deep, and when it stops at that bound, the advice SHALL say so, naming the bound, so a root file beyond it is not silently missed (#402). `chough next` SHALL say when Chough writes are safe: with the three entries in force, that Chough's records may be written and committed at any point of the native order; without them, that Chough's records are committed before `change check --commit` and nothing under `.chough/` is written until finalize. While SpecSync covers the whole repository, through `source_dirs` holding `.` in `.specsync/config.toml` or `.` in the policy's `meaningful_paths`, SpecSync refuses those entries as overlapping, so the advice of `chough doctor` and `chough init` SHALL instead name those settings, say why (SpecSync refuses an entry that overlaps them and, for `source_dirs`, counts the skill bundle `chough init` installs as uncovered source), and say to narrow `source_dirs` to the folders that hold the code, for example `["src"]`, and keep `.` out of `meaningful_paths`, then list the missing entries; When a file a spec covers sits at the repository root, so there is no code folder to narrow to (#354), the advice SHALL instead say to add the skill bundle's and Chough's folders (`.chough`, and `.agents` or the host's skill folder) to `exclude_dirs`, which keeps them out of coverage, and that the list needs the code moved into a folder or SpecSync's fix, CorvidLabs/spec-sync#1083. `chough init` SHALL give its advice with no policy too, and Chough SHALL write neither file. When SpecSync refuses the list because an open change's affected paths overlap it, Chough SHALL pass that refusal through and name the change. Trace: DRIVE-4, FLOW-16.

Acceptance Criteria
- With the three entries listed and real SpecSync at the CI pin, an untracked evidence entry present while `change check --commit` runs leaves verification current in that tree and in a clean clone of the pushed commit, whose workspace digest matches the recorded one (spec-sync #1045's case); the same steps without the entries leave the clone's verification stale, as the control.
- With the three entries listed, a `chough checkpoint`, a `chough evidence add` and a `chough bug add` written after `change check --commit`, and then committed, leave `specsync change status` reporting verification current and the audit passing, and the review then records (the #212 case); without the entries the same writes make verification stale, as the control.
- A case definition changed under `.chough/cases/` after `change check --commit` still makes verification stale, so nothing a change's verification needs is hidden.
- With a prefix missing, `chough doctor` reports `records_in_verification` naming the missing entries and writes nothing; with all three listed it reports nothing; `.specsync/sdd.json` is byte-identical after every Chough command.
- `chough next` says Chough's writes are safe at any point with the entries in force, and gives the commit-first order without them.
- With `source_dirs = ["."]` and no policy, `chough init` prints the narrowing advice naming it, the overlap refusal and the skill bundle; with a policy whose `meaningful_paths` also holds `.`, `chough doctor`'s `records_in_verification` names both settings and says to narrow, then list the missing entries; once both are narrowed the advice is the list again; `.specsync/config.toml` and `.specsync/sdd.json` stay byte-identical.
- With `source_dirs = ["."]` and a spec covering a file at the repository root, `chough init` and `chough doctor` advise adding `.chough` and the installed skill folder to `exclude_dirs` and say the list needs the code in a folder or CorvidLabs/spec-sync#1083, never naming a folder to narrow to; once those folders are excluded, only the list's part is left.
- With `specs/` holding a symlink to a spec file outside the project, a folder symlink that points outside the project and two folder symlinks back to the project, `chough doctor` and `chough init` finish and give the advice they give without them; a `specs/` with more entries than the bound gives the advice with a note naming the bound (#402).
