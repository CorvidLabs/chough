# Chough 0.6.0: commands over human-first records, gates that hold their own stage, approval as the human, and no proof trimming

## MODIFIED

### REQUIREMENT REQ-cli-007

Canonical checkpoint. The helper SHALL keep one canonical checkpoint per open session: the front matter of the active session's `session.md` (REQ-records-004, REQ-cli-037), holding the objective, intent scope, modules, current stage with its status, iteration and side-stage callers, the native change identity, the pull request, referenced criteria, requirements, cases, design sources and files, observation and bug references, blockers, awaiting-human gates, run consents and the next action, with decisions, completed work and open questions in the story sections of the same file. No other writable checkpoint store SHALL exist and no adapter such as APS SHALL be required. Every read SHALL validate the front matter's keys and value types and SHALL refuse a malformed one naming the file, the key and the rule (REQ-records-001). `chough checkpoint --merge` and the `chough-session` merge driver are removed, because each session has its own folder and parallel branches never write one checkpoint (DRIVE-24). When SpecSync is configured, `chough checkpoint --native-change <id>` SHALL read `specsync change status <id>` before it applies any update, and SHALL refuse as `refused:native-change-unknown`, naming the ID and that status command, when SpecSync does not report the change; a failed or timed-out read SHALL also refuse, and a reply whose `summary.id` or `change.id` names a different change SHALL refuse as `refused:native-change-mismatch`, naming both IDs. A JSON reply that names neither `summary.id` nor `change.id` SHALL refuse as `refused:native-change-unknown`, since it does not identify the requested change. Every such refusal SHALL leave the session file byte-identical, including the other updates given in the same call. An ID SpecSync reports, archived or open, SHALL be saved as before. Without a SpecSync configuration only the existing ID format check SHALL apply, with no native read. Trace: FLOW-13, LIFE-3, DRIVE-3, DRIVE-24, DRIVE-25.

Acceptance Criteria
- A checkpoint saved by one process is read unchanged by `chough context` and `chough next` in another process; a front matter key with the wrong type is refused naming the file and the key, with nothing written.
- No second writable checkpoint store is introduced and no adapter is required; `.gitattributes` declares no `chough-session` driver and `chough checkpoint --merge` is not a command.
- With SpecSync configured, `checkpoint --native-change` for an ID SpecSync does not report, or after a failed or timed-out status read, exits non-zero with `refused:native-change-unknown` or the read failure and leaves the session file byte-identical even with other updates in the same call; a reply naming a different change refuses as `refused:native-change-mismatch` with the file byte-identical; a JSON reply naming no change ID, such as `[]` or `{}`, refuses as `refused:native-change-unknown` with the file byte-identical; a reported ID saves; without SpecSync any well-formed ID saves and a malformed one is refused.

### REQUIREMENT REQ-cli-011

Honest case execution. When explicitly invoked, the helper SHALL execute an automated case's binding directly without a shell, with the binding's declared environment set on top of the inherited one, capture its output to the local log of REQ-records-005, and record an evidence entry (REQ-cli-017) linked to the case and its definition digest. Execution SHALL end by the binding's deadline: on the deadline, or when output stays open after the command exits, the helper SHALL stop the command and its descendants and SHALL NOT wait on output it cannot complete. On Unix, when the helper is stopped by SIGINT, SIGTERM or SIGHUP while it runs a binding, a native read or one of its own Git commands, or while it saves what a binding reported, it SHALL stop every command it started together with that command's process group and, on Linux, every descendant that left that group (for example with `setsid`), including one orphaned by its parent, record nothing partial and end by that signal: a stop before an automated case's save begins SHALL record no evidence entry, log or checkpoint change, and a stop that arrives once the save has begun SHALL let the log and the entry both be written before the helper ends by that signal. A signal inherited as ignored, or as blocked in the signal mask, SHALL keep its inherited disposition. When a descendant of one of the helper's own Git commands keeps that command's output open past the grace period and is stopped, the helper SHALL say so on stderr; when its `git rev-parse HEAD` fails for a reason other than an absent repository or a HEAD with no commit, it SHALL say so on stderr and record no revision. Captured output SHALL be bounded per stream while reading. The log SHALL keep the captured bytes, and the entry their SHA-256 and key failing lines (REQ-records-005), while assertions SHALL be evaluated on that text with complete terminal escape sequences removed. Removal SHALL never remove a line break, and a sequence that does not complete before a line break or the end of the output SHALL be left unchanged. The observation SHALL be passed only when the process exits zero, its capture is complete and the binding's assertion holds: exactly one test ran for the `cargo-test` adapter, or every declared expected-output fragment appeared for the `command` and `fledge-task` adapters. Every observation of an executed case SHALL state as a limitation that inherited environment variables were not recorded; when the binding declares variables it SHALL also name them without their values, and when escape sequences were removed it SHALL say so. A run in which no test matched SHALL be recorded as not-run. A repeated run SHALL record one evidence entry holding each attempt and a summary with attempt and failure counts and elapsed time, and SHALL start no further attempt once a stop request or a paused checkpoint exists, including after waiting its interval. Automatic observation and repeated validation run allocation SHALL follow REQ-cli-023. An explicit evidence ID SHALL remain optional for automated and manual case recording; when omitted, the helper SHALL name the entry by REQ-records-003, and when supplied for a new write it SHALL be a date and slug name not in use. An old-style supplied ID SHALL be refused with a remedy to omit the ID. The automated log SHALL be exactly `.chough/local/logs/<evidence id>.log`, inheriting the entry's name, and SHALL NOT be committed. Observation and validation run IDs from 0.5.x SHALL stay readable and resumable as aliases. A successful `cases record` response SHALL retain every existing key and SHALL add `case` and `observation`, containing the recorded case ID and observation ID respectively; the observation ID SHALL equal both the evidence file stem in `recorded` and the stored record's `id`. Trace: FLOW-7, FLOW-9, LIFE-7, FLOW-14, LIFE-19, KNOW-35.

Acceptance Criteria
- A deliberately failing assertion records failed even when another case passes in the same session.
- A cargo filter that matches no test records not-run, never passed.
- Changing a case definition reports its earlier observations as stale-case-definition.
- A case whose descendant holds its output returns by its deadline, and its descendants are stopped.
- SIGINT, SIGTERM or SIGHUP during `cases run` before its save begins, during a native read in `next`, or during the Git that `stage backfill` or `library snapshot` runs before writing leaves no process Chough started, Git included, and no new or changed `.chough` or library file; a stop once a case run's save has begun leaves both its log and its evidence entry, and no process Chough started.
- A stop request made during the interval halts a repeated run before the next attempt, and resuming continues with the stored limits.
- A declared variable reaches the command, and the observation names it without its value.
- An observation of a case that declares no variables still states that inherited environment variables were not recorded.
- An escape sequence interrupted by a line break or the end of the output is left unchanged, and removal never lowers the number of lines that start with `test result:`.
- Coloured output whose visible text holds a fragment passes with the escape limitation, the log stays byte-exact, and a fragment absent from the visible text still fails.
- Omitting the evidence ID names the entry `<date>-<case slug>`, identical repeated runs on one day receive distinct names, and each automated log is exactly `.chough/local/logs/<evidence id>.log`, ignored by Git.
- Repeated validation records one entry named `<date>-<case slug>-run` with every attempt. Migrated observation and validation IDs remain readable and resumable as aliases, while an old-style ID supplied for a new case observation fails with an omit-ID remedy.
- On Linux, SIGTERM during `cases run` also stops a descendant that called `setsid`, and one whose parent exited after starting it with `setsid`.
- A Git descendant that holds output past the grace period is stopped with a stderr notice, and a failed `git rev-parse HEAD` is reported on stderr while the transition is still recorded.
- A successful `cases record` response returns `case` and `observation` beside every pre-existing key; `observation` equals the `recorded` path's file stem and the stored record's `id`.

### REQUIREMENT REQ-cli-012

Local bug backlog. The helper SHALL keep each bug as one Markdown record, `.chough/bugs/<id>.md` (REQ-records-001), whose front matter gives `kind: bug`, `id`, `aliases`, `title`, `status`, `classification`, `scope`, `impact`, `criteria`, `requirements`, `cases`, `evidence` (the linked evidence IDs), `receipts` (the receipt fields of REQ-history-006 for linked evidence no longer in an open session), `regression_baseline`, `fixture`, `environment`, `revision`, `found_by` (the actor, REQ-records-007), `fixed_in`, `duplicate_of`, `related`, `created` and `updated`, and whose body gives `# <title>` and the paragraphs What happened (the symptom and actual behavior), Steps (the trigger), Expected, Why it matters and Fix, then `## Log`, an append-only list with one dated entry per report, note, evidence link and status change. It SHALL list open bugs for a fresh session and SHALL search existing records by symptom, trigger and affected IDs before a new record is added. A bug SHALL remain unverified until a failed observation is linked, and a regression classification SHALL require a passed observation at an ancestor revision. A bug SHALL read as reproduced and later passed, and SHALL accept the verified status, only when a present linked passed observation was observed strictly after its most recent present linked failed observation; a receipt counts as present, and an observation shown as removed (REQ-records-009) does not. Additional evidence SHALL be appended to the Log, never overwriting anything. A bug in another tool's behaviour MAY be closed as `fixed-upstream` with `bug update --status fixed-upstream --note <text>`, the note naming the upstream fix and who checked it where; it is a closed status, as `verified`, `duplicate` and `wont-fix` are, needs no Chough observation, and SHALL never read as verified by Chough. The helper SHALL render a report candidate and SHALL NOT publish it. Every new bug SHALL be named by REQ-records-003 from its title, the same for manual `bug add` and automatic failure capture, and written by create-new; an update SHALL NOT rename the record, even when its title has changed. Every `BUG-NNNN` and `BUG-<slug>-<hex>` ID from 0.5.x SHALL resolve as an alias, and duplicate and related links SHALL resolve in either direction across aliases and new names. Documentation SHALL state that Chough 0.5.x cannot read 0.6.0 bug records. Trace: FLOW-8, LIFE-5, LIFE-8, DRIVE-25, DRIVE-27.

Acceptance Criteria
- A sample failure becomes a reproduced and classified bug; a second report of the same symptom is found by search and its evidence is appended to the Log.
- A regression classification without a passed observation at an ancestor revision is refused.
- An out-of-scope bug stays in the open backlog without changing the checkpoint scope.
- Rendering a report candidate prints Markdown and performs no network action.
- A pass observed before, or in the same second as, the latest linked failure leaves the bug reproduced and the verified status is refused; a bug with no linked failure cannot be marked verified.
- `--classification blocking` is refused with a hint to use `--scope`, and `--scope product-defect` with a hint to use `--classification`.
- Manual `bug add` and automatic failure capture both name the bug `<date>-<title slug>`, and changing a stored title and then updating its status or evidence leaves the name unchanged.
- Each update appends one Log entry and leaves every earlier Log line, and every body paragraph a person wrote, byte-identical.
- A migrated bug answers to its `BUG-NNNN` alias in list, search, show, update and report, and duplicate and related links resolve from alias to new name and back.
- After the session holding a bug's linked evidence is archived, the bug resolves that evidence to the story's receipt and its verified state is unchanged.
- The CLI documentation says Chough 0.5.x cannot read 0.6.0 bug records.
- `bug update --status fixed-upstream` without a note is refused; with one it closes the bug, `bug list` shows it closed as fixed upstream, and nothing reports it verified.

Then no transition SHALL be recorded and the checkpoint SHALL stay byte-identical. Otherwise the helper SHALL record one `advance` transition per step, in order, each with its own gate label and the given note. It SHALL report the steps in order in `applied.steps`, with `applied.from` as the starting stage, `applied.to` as the target and `applied.gate` as the last step's label. `stage advance` without `--to` SHALL be unchanged.

### REQUIREMENT REQ-cli-054

Bug value, deduplication and report mappings. `chough bug add` and `chough bug update` SHALL accept exactly the six classifications (unclassified, product-defect, regression, environment, requirement-gap, evidence-gap), the three scopes (blocking, in-scope, out-of-scope) and the eight statuses (open, investigating, fix-pending-verification, verified, deferred, duplicate, wont-fix, fixed-upstream), and SHALL refuse any other value naming the allowed ones, with nothing written; `fixed-upstream` SHALL be accepted only with a `--note` that is not blank (REQ-cli-012). Four statuses are closed: verified, duplicate, wont-fix and fixed-upstream. A bug SHALL block leaving test only while its scope is blocking and its status is not closed, so a bug in a closed status never blocks. Search SHALL score the word overlap of a report with each bug's title, symptom and trigger, adding 0.25 when they share a criterion, requirement or case; it SHALL list matches from 0.2 and refuse a new bug only from 0.5, naming `chough bug update <id> --observation <id> --note <text>` and `--distinct <why this is a different defect>`. A distinct reason SHALL NOT be blank and SHALL be kept in the new bug's notes. A duplicate or related link SHALL name another existing bug: a link to the bug itself or to an unknown bug, and an update or report of an unknown bug, SHALL be refused with nothing written, naming `chough bug list --all`. Changing the status of a duplicate bug SHALL clear its `duplicate_of` link and record that in its notes, so a mistaken duplicate can be reopened. Marking a bug verified without a linked failure and a later linked pass SHALL name `chough bug update <id> --observation <id>`. The report candidate SHALL show every stored field, and `none recorded` (for steps, `Not recorded.`) for each empty one. Trace: FLOW-8, LIFE-5.

Acceptance Criteria
- Each classification, scope and status is accepted on add or update and recorded; any other value is refused with the allowed list and the record stays byte-identical; `--status fixed-upstream` without a note is refused with nothing written.
- Of every scope and status, only an open bug with scope blocking is listed as blocking and stops leaving test; making it wont-fix or fixed-upstream releases the gate.
- A report sharing only a requirement with a bug is listed by search at 0.25 and added without `--distinct`; one sharing its words is refused, naming both ways forward; a blank distinct reason is refused with nothing written, and a given one is kept in the new bug's notes.
- Linking a bug to itself or to an unknown bug, as duplicate or related, and updating or reporting an unknown bug, are refused with nothing written and name `chough bug list --all`, which lists the bugs.
- A bug marked duplicate by mistake is reopened with `chough bug update <id> --status open`, which clears `duplicate_of` and notes it; marking it verified without a linked failure names `chough bug update <id> --observation <id>`, and linking a failure and a later pass then verifies it.
- The report shows every stored field of a fully recorded bug, and `none recorded` (for steps, `Not recorded.`) for each empty one.

### REQUIREMENT REQ-cli-059

The closed gate's relay SHALL then carry the summary digest and the list (REQ-history-014). Each refusal SHALL name the command that recovers. When the named gate drives review (REQ-cli-030) and the change has no current scoped review, it SHALL first record the review as the decided human with verdict `pass`, since a ship is run only on acceptance, as REQ-records-008 says, and SHALL stop with nothing more run or written when that review is refused. When SpecSync exits non-zero, it SHALL exit with that code and write nothing. When SpecSync succeeds, it SHALL close the named gate as `chough checkpoint --close-gate` would, a relayed claim, and then move the session to done as `chough stage advance --to done` would, printing each step's report after SpecSync's output. When either step refuses after a successful ship, it SHALL exit 1, say that the change was shipped, and name each remaining command. Stopping Chough with SIGINT, SIGTERM or SIGHUP SHALL stop the SpecSync process it started (FLOW-14). The review step follows FLOW-23.

- When the move into done is refused after a successful ship, the exit is 1, the output says the change was shipped and names `chough stage advance --to done`, and that command then succeeds.

### REQUIREMENT REQ-cli-061

Gate lists. `chough gate list [--json]` SHALL number every open human gate of every open session in the project from 1, with the stage it holds and the native step it drives (REQ-cli-030). It SHALL give each a one-screen summary of at most 24 lines and 4,096 bytes, with:
- what changed: the files, insertions and deletions from the merge base of HEAD with the default branch (`origin/HEAD`, else `main`), or from the change's `base_commit` (from its `state.json`) when there is no merge base, leaving out `.chough/`, the knowledge directory and SpecSync lifecycle bookkeeping, and naming the five files with the most changed lines among the rest (#190);
- the tests: how many cases passed, failed and were not run, by the latest observation of each case that links a requirement the change's deltas add or modify, or that the session's observations name, with the failing case IDs;
- the risks: the first 8 lines of the change's `plan.md` section "Risks", or "none recorded";
- a diff link: the GitHub compare URL from the base to HEAD when `origin` is a GitHub remote, otherwise `git diff <base>..<HEAD>`.

Each summary's digest SHALL be the SHA-256 of its text. The list SHALL be saved as `.chough/local/gate-lists/<list>.json`, where `<list>` is the first 12 hex digits of the SHA-256 of the list. Listing SHALL make no native read and write no tracked file.

`chough gate record <list> --gates <n>[,<n>...] --decided-by <who> --words <words> --where <where> --recorded-by <agent>` SHALL close each named gate as `chough checkpoint --close-gate` would with the four values (REQ-cli-050), and its relay SHALL carry that gate's `summary_digest` and the `list` (REQ-history-014). - an unknown list, a number not on it, a listed gate that is no longer open, or a gate whose summary's digest has changed, each naming `chough gate list`;
- a gate whose change's `state.json` state is `verifying`, naming `chough change ship <id> --list <list> --gate <n>` with the relay;

A named gate that drives a native step SHALL run it as the decided human (REQ-records-008) before any gate is closed.

Acceptance Criteria
