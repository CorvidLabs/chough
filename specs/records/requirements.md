# Records requirements

The requirements of this module are added by the Chough 0.6.0 change (human-first
records) when `specsync change check` applies its approved delta.

### REQ-records-001

Record files. Every record Chough writes, a session, an archived session story, an evidence entry, a bug, an inbox entry, a journal post and a migration receipt, SHALL be one UTF-8 Markdown file that starts with YAML front matter between two `---` lines, and that file SHALL be the record's only source of truth: no JSON or other twin SHALL be written beside it, and no index, cache or generated note SHALL be read in its place. The front matter SHALL carry the IDs and fields agents parse; the body SHALL carry the record for a human reader. Front matter SHALL use a strict subset of YAML that Chough reads and writes without a new dependency: `key: value` scalars, plain or double-quoted with `\"`, `\\` and `\n` escapes; flow lists `[a, b]`; block lists of scalars; and block lists of flat maps of scalars. Chough SHALL refuse front matter outside that subset, a duplicate key or a missing closing `---`, naming the file, the line and the rule, and SHALL write nothing in that command. A record's body SHALL NOT hold a Git conflict marker: a line that starts with `<<<<<<<` or `>>>>>>>`, or a line of `=======` between such lines (a `=======` line outside them, as a Markdown heading underline, is not one); a line inside a closed fenced code block, as CommonMark reads one, quoting an example or tool output, is not one, but a fence that never closes hides nothing after it, and no fence hides a conflict in a section Chough writes itself, a session's `## Timeline` or an archived story's `## Receipts` (#339). A real conflict Git leaves inside such a fence cannot be told from a quoted one, so no write SHALL be refused for it, and `chough doctor` SHALL only warn of each marker line there (REQ-cli-055). A lone `=======` outside a conflict may be left by a half-resolved conflict, but a heading underline may be followed directly by text, so no write SHALL be refused for it, and `chough doctor` SHALL only warn of it (REQ-cli-055). Chough SHALL refuse a write whose body would hold one as `refused:conflict-markers`, naming the file, the line and the marker, with every file unchanged, and `chough doctor` SHALL report each committed record whose front matter or body holds one as a `conflict_markers` finding naming the file, the line and the marker, which has no fix (#374). A marker SHALL be named by its seven characters only, never the rest of its line, which may carry a branch name or a commit subject (#365). Reading SHALL be tolerant: an unknown front matter key SHALL be kept byte for byte, in place, when Chough rewrites the front matter, and SHALL be ignored otherwise; a missing optional key SHALL take its documented default; CRLF line endings SHALL be read as LF. Chough SHALL own only the front matter and the sections it appends to, and SHALL keep every other body byte a person or agent wrote: a write SHALL replace the front matter, append list items to the end of a named section, or create a missing named section at the end of the body, and SHALL do nothing else to an existing body. Files SHALL be written with LF line endings by an atomic replace under the writer lock of REQ-cli-040, or by create-new for a new record. A record SHALL be at most 65,536 bytes, except a session record, an archived session story and a migration receipt, which SHALL be at most 1,048,576, 1,048,576 and 4,194,304 bytes; a record over its bound SHALL be refused with the bound named and every file byte-identical. When a 0.5.x record would migrate into a record that holds a marker, the preview SHALL say that the apply refuses and SHALL NOT offer the apply command, and `chough migrate --apply` SHALL refuse with nothing written, each naming the 0.5.x file to resolve, the record it would become, the line and the marker. Trace: DRIVE-25, DRIVE-26, DRIVE-28, KNOW-32, LIFE-3.

Acceptance Criteria
- Every record kind written by a fixture cycle (session, archived story, evidence, bug, inbox entry, journal post, migration receipt) starts with front matter that the reader parses, and no `.json` file is written under `.chough/` except the local caches of REQ-history-007 and `.chough/preferences.json`.
- A person's edit to a session's Goal paragraph, to a bug's Steps and to an evidence entry's body survives a following stage move, decision, evidence add and bug update byte for byte.
- An unknown front matter key added by hand is kept byte for byte after Chough rewrites that front matter, and a missing optional key reads as its default.
- Front matter with a nested map, an anchor, a duplicate key or no closing line is refused with the file, line and rule named, and nothing is written.
- A CRLF copy of a record reads the same as the LF original.
- A record one byte over its bound is refused naming the bound, with every file unchanged.
- A record write whose body holds a `<<<<<<<`, `=======` or `>>>>>>>` conflict line is refused as `refused:conflict-markers` naming the file, the line and the marker, with every file unchanged; a body with a `=======` heading underline and no conflict is written.
- With a committed record whose body holds a conflict, `chough doctor` reports a `conflict_markers` finding for each marker line naming the file, the line and the marker, exits 1, and reports none for a tracked file that is not a record.
- A conflict quoted inside a fenced code block, with backtick or tilde fences, is not a marker and the record saves; a lone `=======` with text after it is not refused either.
- A conflict after a code fence that never closes, or after a backtick line whose tag holds a backtick, is a marker and the write is refused.
- A conflict inside an archived story's `## Timeline` or fenced `## Receipts` block is a marker, inside a fence or not.
- A Git conflict left inside a code fence of a session's Goal is not refused on the next write.
- A 0.5.x inbox entry whose text holds a conflict makes the migration preview say the apply refuses, without offering the apply command, and the apply refuse, each naming that 0.5.x file first.
- A conflict whose marker lines name a branch or a commit subject holding a token is refused and reported naming only `<<<<<<<`, `=======` or `>>>>>>>` and the line, never the branch or the subject (#365).
- A committed record whose front matter holds a conflict, as two branches that each set `--objective` leave after a merge, gives a `conflict_markers` finding for each of its marker lines (#374).
- A new record whose write fails or is cut off, as by a full disk or a file-size limit, leaves no file at its name and no temporary file beside it, the command exits non-zero naming the record, and every reader works as it did before; an empty record file is named as empty, with the way out, rather than as a record missing its `---` line.

### REQ-records-002

The records tree and its reading guides. Chough's committed records SHALL live in this tree: `.chough/README.md`; `.chough/sessions/<id>/session.md` with its `evidence/` and `agent/` folders, for open sessions; `.chough/archive/sessions/<id>.md`, one file per finished session, with `.chough/archive/sessions/<id>/` beside it only for its key screenshots (REQ-records-013); `.chough/archive/shelved/<id>/`, for shelved sessions; `.chough/archive/migrations/<id>.md`, for migration receipts; `.chough/bugs/<id>.md`; `.chough/cases/*.cases.toml`, case definitions in their existing TOML format (REQ-cli-009, REQ-cli-047); `.chough/preferences.json` (REQ-cli-013); and, kept from 0.5.x, the files under `.chough/artifacts/` that an open bug names as its fixture (REQ-records-009). Machine-local facts SHALL live only in the Git-ignored `.chough/local/` (REQ-history-007). Each kind of file SHALL have a stated rule: a session folder lives while its work is open and leaves the tree once its story is written and its bytes are committed; an archived story stays for good; a bug file stays for good; case definitions and preferences are configuration a person edits; and machine-only files live in `.chough/local/` and are never committed. `chough init` and `chough migrate --apply` SHALL write `.chough/README.md` create-only, a one-screen guide in plain words that names each folder, what it holds and its rule, which folder is never committed, and that intent lives in `hi/`, contracts in `specs/` and change history in `.specsync/archive/`, each a link, with no copy of their content; an existing `.chough/README.md` SHALL be kept byte-identical. `knowledge/index.md` is the vault's reading guide (REQ-cli-043). Chough SHALL write no other committed file or folder under `.chough/`, and SHALL NOT read a 0.5.x path except in `chough migrate` and `chough doctor` (REQ-records-010). Trace: DRIVE-24, DRIVE-28, KNOW-32, KNOW-24.

Acceptance Criteria
- After `chough init` in a new project, `.chough/` holds `README.md`, `cases/` and `local/` (ignored by Git), and `.chough/README.md` names every folder of the tree, says that `local/` is never committed, and links `hi/`, `specs/` and `.specsync/archive/`.
- `chough init` and `chough migrate --apply` over an existing `.chough/README.md` keep it byte-identical.
- A full fixture cycle, from session new through done with a bug, cases and evidence, leaves committed files under `.chough/` only at the paths this requirement lists.

### REQ-records-003

Date and slug names. A new session, evidence entry, bug, inbox entry, journal post and migration receipt SHALL be named `<YYYY-MM-DD>-<slug>`, the date being the UTC date of its creation and the slug the lowercase ASCII letters and digits of its source (a session key, a case ID or claim, a bug title, a post title), each maximal run of other characters replaced by one hyphen and leading and trailing hyphens trimmed, with the record kind as the slug when nothing is left. The whole name SHALL be at most 80 bytes, the slug cut back at a hyphen when it would exceed that. A record SHALL never be named by a sequence number, a counter or a high-water mark. When a file of that name already exists in the same folder at creation, the new record SHALL get `-` and 6 lowercase hexadecimal digits from 24 fresh random bits (REQ-cli-023's random source), written by create-new; if that name also exists the write SHALL be refused, with nothing written, and SHALL NOT draw again. A record's name SHALL NOT change after creation. The record's front matter SHALL give its name as `id`. Every ID a record had before 0.6.0 (a `BUG-NNNN` or `BUG-<slug>-<hex>` bug, an `OBS-`, `VAL-` or `SNAP-` record, a session key) SHALL be kept in its front matter `aliases` list, and every command and link that takes a record ID SHALL resolve it by `id` or by alias; an alias held by two records SHALL be refused by the command that resolves it and reported by `chough doctor` (REQ-history-012). SpecSync requirement IDs, case IDs, lesson numbering and spec versions SHALL keep their schemes. Trace: DRIVE-27, DRIVE-12, DRIVE-25.

Acceptance Criteria
- `  Fix   LOGIN... now!  ` recorded as a bug on 2026-11-10 is named `2026-11-10-fix-login-now`, and a title with no letter or digit gives `2026-11-10-bug`; an overlong title gives a name of at most 80 bytes that ends without a hyphen.
- Two bugs with the same title on the same day get `2026-11-10-<slug>` and `2026-11-10-<slug>-<6 hex>`; a forced clash of the suffix too is refused with nothing written and no second draw.
- Two branches that each add a bug and an evidence entry on the same day with different titles merge with no conflict.
- A migrated bug with alias `BUG-0012` is shown, updated and linked by `BUG-0012` and by its new name, and a session referencing `OBS-<slug>-<hex>` resolves it to the migrated evidence; an alias given to two records is refused by `bug show` and reported by `chough doctor`.
- No new record's name holds a number taken from a count of existing records.

### REQ-records-004

The session record. An open session's `session.md` front matter SHALL be its checkpoint and SHALL give `kind: session`, `id`, `aliases`, `objective`, `intent_scope`, `modules`, `stage`, `stage_status`, `iteration`, `callers`, `native_change`, `pr`, `criteria`, `requirements`, `cases`, `design`, `files`, `observations`, `bugs`, `blockers`, `waiting_on_human` (each gate with `gate`, `holds` and `opened`, REQ-cli-030), `run_consents` and `next`. Its body SHALL be the story, in these sections in this order: `# <title>` (the objective), `## Goal`, `## Where it stands`, `## Decisions and why`, `## What was verified`, `## Open threads` and `## Timeline` (REQ-history-002), whose entries carry the fields that requirement lists and the reason a gate was withdrawn (REQ-history-012). A decision recorded with `chough checkpoint --decision` SHALL be one list item appended to Decisions and why, naming who decided when the decision is a human's (REQ-cli-050) and linking the gate's timeline entry; completed work SHALL be appended to Where it stands; an open question SHALL be one list item in Open threads, resolved by appending its answer to that item's line through `chough checkpoint --resolve-question`; an evidence entry referenced by the session SHALL be one list item in What was verified that links its file. These sections SHALL be the only place the session keeps decisions, completed work and open questions, and `chough next` and `chough status` SHALL read them there (REQ-cli-021), so no field repeats them. Chough SHALL write the Goal from the objective when the session is created and SHALL NOT rewrite the Goal or Where it stands paragraphs afterwards, with one exception: while the `# <title>` line or the Goal still holds, untouched, the placeholder objective `chough session new` writes when none is given, the next save after the objective is set SHALL fill each such one with the objective, once, so the story and its journal post carry the objective and never the placeholder; a title or Goal a person wrote SHALL never be rewritten. Trace: DRIVE-24, DRIVE-25, DRIVE-26, FLOW-13.

Acceptance Criteria
- `chough session new` writes a `session.md` whose front matter carries every listed key and whose body has the seven parts in order with the Goal taken from the objective.
- A decision, a completed item, an open question and an evidence reference each appear once, in their section, and `chough next` shows the same decision and question from a fresh process.
- Resolving an open question keeps its line and appends the answer, and `chough next` no longer lists it as open.
- A person's rewrite of the Goal paragraph is kept after a decision and a stage move.
- A session started without an objective, given one with `chough checkpoint --objective`, has that objective as its title and Goal; a later objective change rewrites neither, its journal post and archived story carry the objective and not the placeholder, and a Goal a person wrote over the placeholder is kept byte for byte.
- A session whose body holds a code fence that never closes, as a Goal that is three backticks, saves any number of times with each of its sections once, and `chough next` reads its decisions and open questions: such a fence hides nothing after it, as it hides no conflict (REQ-records-001), while a closed fence still hides the headings it quotes.

### REQ-records-005

Proof files: logs, key failing lines and external evidence. A raw log SHALL never be committed. The raw output of an executed case SHALL be written to `.chough/local/logs/<evidence id>.log`, and its evidence entry SHALL give the exact command, the SHA-256 of the captured output as its fingerprint and, when a CI run holds the log, `raw_log` naming that run. For a failed or not-run case run, the entry's body SHALL also keep the key failing lines: at most 20 lines and 2,048 bytes of the captured output, with complete terminal escape sequences removed, taken for the `cargo-test` adapter from the first failure block and the `test result:` line, and otherwise from the last non-blank lines of standard error and then standard output; any of them that matches REQ-records-006 SHALL be redacted, never refused, and the entry SHALL say how many were. `chough evidence add --failing-lines <text>` SHALL keep the same for a manual failure, within the same bounds and checked as REQ-records-006 checks other text. `chough evidence add --artifact <path>` and `chough cases record --artifact <path>` SHALL accept an absolute path outside the project: Chough SHALL fingerprint it in place with SHA-256 within a 64 MiB bound and SHALL NOT copy it into the repository; a missing path, a directory, a symlink and a file over 64 MiB SHALL be refused, naming the path on standard error only. It SHALL record the path and fingerprint in `.chough/local/external-artifacts.toml` under a neutral ID `ext-<6 lowercase hex>` from fresh random bits, written by create-new, and the committed entry SHALL give only `external: ext-<hex>` and `fingerprint: sha256:<64 hex>`. On the machine that holds the ID, freshness SHALL re-read the file and report the artifact `current` or `changed`; elsewhere it SHALL be reported `external, not checkable here`, which SHALL be neither a pass nor a staleness of the entry's own content identity. A path outside the project, a local tool path and a raw log SHALL be kept only in `.chough/local/`. Key screenshots are committed under REQ-records-013. Trace: KNOW-35, LIFE-19, FLOW-22, LIFE-26, LIFE-8.

Acceptance Criteria
- `chough cases run` writes its captured output to `.chough/local/logs/`, and the committed entry carries the exact command and the output's SHA-256; no file Git tracks under `.chough/` holds a raw log.
- A failing `cargo-test` case's entry keeps its panic lines and its `test result:` line, at most 20 lines and 2,048 bytes, with no escape sequence; a failing line holding a home path is stored as `<redacted:home-path>` and the entry counts it.
- An absolute artifact outside the project is fingerprinted in place, its path appears only in `.chough/local/external-artifacts.toml`, and the committed entry holds only the neutral ID and the fingerprint.
- A missing path, a directory, a symlink and a 64 MiB plus one byte file are refused with nothing recorded.
- Changing the external file makes the artifact read `changed` on that machine; with `.chough/local/` removed the entry reads `external, not checkable here` and is neither reported passed nor stale because of that artifact.

### REQ-records-006

No leaks in committed records. Before writing any committed record, Chough SHALL check every value it writes, in front matter and body, including recorded commands, summaries, reasons, decisions, answers to questions, relayed words and places, notes, limitations, titles, module names and actor values, for: an absolute path under a home, temporary or system root (`/Users/`, `/home/`, `/root/`, `/private/`, `/tmp/`, `/var/`, `/Volumes/`, `/mnt/`) or a Windows drive path; a `~/` or `~<user>/` path; the local host name anywhere when it is at least 8 characters long or holds a digit, a hyphen or a dot, and a shorter all-letter host name, which may be an ordinary word, only inside a path or a URL or as `<user>@<host>`, or as the `<host>:/<absolute path>` of an scp-style remote path, where the local host names are the machine's host name, its first label and, on macOS, its LocalHostName, each also as `<name>.local`, and one holding a dot counts inside a hyphenated name too, as in `build-<host>-1` (#368); and a host label equal to the local user name, case-insensitive, SHALL NOT count as a path component, since the user-name rules already own that name and it may be an ordinary folder, as a source directory, while the same name still counts in a URL, as `<user>@<host>` and as the host of an scp-style path; and the local user name, checked as the account's name and also as each of `USER`, `LOGNAME` and `USERNAME` that is set (#379), when it appears inside an absolute path, except as the first component of one that names a system root such as `/dev/`, after `~`, or as `<user>@<host>`. A relative path or a web URL (`http:` or `https:`) holds no user name, while a local file URL (`file:`) is checked like the path it carries, and the name `root` never counts (#379); an email address; and credentials: GitHub, GitLab, Slack (bot, user, workspace and `xapp-` app tokens), AWS, Hugging Face (`hf_`) and model-provider token forms, private key blocks, bearer and basic authorization values, JSON web tokens, and `password`, `secret`, `secret_key`, `secret_access_key` (as in `AWS_SECRET_ACCESS_KEY`), `token` or `api_key` assignments, with the key quoted or not, as in `{"password": …}`, and a value of 8 or more characters (#368). A value that matches SHALL refuse the write as `refused:leak`, naming the field and the kind of match and never the matched text, with every file byte-identical. With `--redact`, each match SHALL instead be replaced by `<redacted:<kind>>` and the write SHALL proceed, saying how many values were redacted, `chough evidence add` included (#368); a module name is an ID, so it is refused under `--redact` too. An error SHALL show a value a person gave, such as a session name from `--session`, `CHOUGH_SESSION` or `session use`, a bug or evidence reference or a `--decided-by` value, only when the value holds no match and no control character; otherwise it SHALL name the field and what it holds, as in `CHOUGH_SESSION holds token`, never the value (#367). Output that repeats a value given on the command line, such as the environment `chough next` and `chough status` show or the criteria, requirements and paths `chough cases select` lists, SHALL follow the same rule (#367). A human's configured display name (REQ-records-008) SHALL NOT count as a user name. `chough doctor` SHALL scan every file Git tracks under `.chough/`, `knowledge/` and `.specsync/changes/`, except a change's `deltas/`, which hold requirement text as `specs/` does, for the same patterns and SHALL report each as a `leak` finding with the file, the line and the kind, never the text, except that a path under `/tmp/` or `/private/tmp/` in a case definition (`.chough/cases/*.cases.toml`) is a deliberate test setting, such as a case's own `XDG_DATA_HOME`, and SHALL NOT be reported or offered `--redact`, while a home path, the local user or host name, an email or a credential in a case definition still SHALL; the verify and CI lanes SHALL run that scan and fail on a finding. A finding under `.specsync/changes/` SHALL NOT be redacted by `chough doctor --fix --redact`, which SHALL skip it naming the way out, `chough change answer` or a send-back, since rewriting SpecSync's record would leave the change's approval invalid; `.specsync/archive/`, SpecSync's authenticated history, SHALL NOT be scanned (#412). An scp-style remote path, `<host>:/<absolute path>`, SHALL be checked like the path it carries, so a home or system root after the colon refuses as a path leak and the host part counts as the local host name when it matches. Trace: LIFE-26, LIFE-17, FLOW-22.

Acceptance Criteria
- Each pattern kind, placed in an evidence summary, a decision, a relayed `--words`, a bug note and a recorded command, refuses the write with `refused:leak` naming the field and kind, the output never contains the matched text, and every file is unchanged.
- The same writes with `--redact` store `<redacted:<kind>>` and report the count.
- A decision naming the configured human display name is written; the same name inside `/Users/<name>/` is refused.
- With one committed record holding a home path, `chough doctor` reports a `leak` finding with its file, line and kind, without the path, and exits 1; `fledge lanes run verify` fails on it.
- The records of a full fixture cycle run inside a temporary directory hold no absolute path, user name or host name.
- A committed case definition whose binding sets `XDG_DATA_HOME` to a path under `/tmp/` gives no `leak` finding from `chough doctor`, while one holding a home-folder path still gives one naming the file and line.
- With a short all-letter host name, a record using it as an ordinary word is written and `chough doctor` reports nothing, while the same name inside a path, a URL or as `<user>@<host>` is still refused; a host name of 8 or more characters, or one holding a digit, hyphen or dot, is still refused anywhere.
- With a short all-letter host label equal to the local user name, a record using that name as a path component is written and `chough doctor` reports nothing, while the same name in a URL, as `<user>@<host>` or as the host of an scp-style remote path is still refused; a host label that only equals the user name after another label, or a different name, is still refused as before.
- With an scp-style remote path, `<host>:/<absolute path>`, the write is refused as a path leak when a home or system root follows the colon, and the host part is refused as a host-name leak when it is the local host, in the write guard and in `chough doctor` alike.
- `checkpoint --resolve-question <question> --answer <text>` with each pattern kind refuses with `refused:leak` naming `answer`, with every file unchanged; with `--redact` the answer holds `<redacted:<kind>>`; an answer over 4,096 bytes is refused (#364).
- `{"password": "…"}`, `SECRET_KEY=…`, `AWS_SECRET_ACCESS_KEY=…`, an `xapp-` and an `hf_` token, a `~<user>/` path, the LocalHostName's `<name>.local` and a dotted host name inside `build-<host>-1` each refuse the write; `session new --module` holding a pattern kind is refused (#368).
- With `USER` and `LOGNAME` unset, the account's user name as `<user>@<host>` is still refused; with the user named `dev`, a `/dev/…` path, `src/dev/main.rs` and `https://example.com/dev/guide` are written while `/opt/dev/x` is refused; with the account `root`, `ssh root@build-box` and `postgres://root@db/x` are written; a home path and a `~/` path are still refused (#379).
- `evidence add --redact` with a leaking value says how many values it redacted (#368).
- An unknown session, bug or evidence reference or `--decided-by` value holding a pattern kind or a control character is refused naming the field and what it holds, and the output holds neither the value nor the control character; a clean one is still named (#367).
- With the user named `dev`, `file:///opt/dev/x` is refused as a `user-name` leak, while `https://example.com/dev/guide` is still written; with `USER`, `LOGNAME` and `USERNAME` set to three names, each is refused inside an absolute path.
- A sweep that gives every value a command takes, flag or argument, a token and an escape sequence finds neither in any error or output, including `pref set` and `pref unset`, `consent revoke`, `skill status` and `skill remove-legacy` with `--host`, `stage advance --to`, `stage enter` and `stage back --to`, `validate resume`, an explicit evidence ID, `library merge`, `correct`, `next --environment`, `status --environment`, `cases select`, `change new`'s description, `change answer`'s answer and `change ship --close-gate`; each names the field and what it holds instead (#367, #412).
- With a token committed in an open change's `context.md`, `chough doctor --leaks` reports a `leak` finding with the file, line and kind and exits 1, and `chough doctor --fix --redact` leaves the file byte-identical with the finding skipped, naming the way out; a home path in an open change's delta, and a leak under `.specsync/archive/`, give no finding.

### REQ-records-007

The acting agent. Each timeline entry (REQ-history-002), evidence entry and bug SHALL record the acting agent when it is known, as `actor` with `agent`, `model` and `terminal`, each only when known: `CHOUGH_ACTOR`, `CHOUGH_ACTOR_MODEL` and `CHOUGH_HC_TERMINAL` SHALL set them; otherwise the agent SHALL be `claude-code` when `CLAUDECODE` is set and the terminal SHALL be `HC_TERMINAL_ID` when it is set. The terminal SHALL be the hc terminal address or name, such as `t370`, and never a file path, a host name or a network address. A value that fails the check of REQ-records-006 SHALL be left out with a warning on standard error, and an unknown actor SHALL leave the field out; neither SHALL fail a command. `chough next` and `chough status` SHALL show the last actor, and `chough status` SHALL show each listed evidence entry's actor. The actor is an unauthenticated claim and SHALL never stand in for a human decision (FLOW-16). Trace: LIFE-17, LIFE-26, FLOW-16.

Acceptance Criteria
- With the three override variables set, a stage move, an evidence add and a bug add each record that agent, model and terminal; with only `CLAUDECODE` and `HC_TERMINAL_ID` set they record `claude-code` and that terminal.
- With none set, no record has `actor`, `chough next` shows no last actor, and every command succeeds.
- A terminal value holding a home path is left out with a warning and the command succeeds.
- The shared test fixture clears the five variables, so the suite gives the same records under Claude Code and hc.

### REQ-records-008

A human's gate approval drives the native approval as that human. Chough SHALL read human identities from configuration, never from its source: the user configuration file `chough/identity.toml` under `XDG_CONFIG_HOME` (by default `~/.config`), overridden by `.chough/local/identity.toml` when present, each `[[human]]` giving `name`, the display name records show, optional `aliases`, and `specsync_actor`, the actor SpecSync records. Every close of a gate with a human's decision (REQ-cli-050, REQ-cli-059, REQ-cli-061), whatever the gate drives and with or without `--no-native`, SHALL resolve `--decided-by` to one configured human by name or alias before anything runs or is written. When the gate drives a native step (REQ-cli-030), Chough SHALL then run, before it records anything, `specsync change approve <id> --actor <specsync_actor> --note <note> --words <words> --where <where> --recorded-by <agent>` for a gate that drives approval, the note giving the human's exact words, where and when they decided, and the agent that relayed or recorded it, or `specsync change review <id> --reviewer <specsync_actor> --verdict <pass or block> --words <words> --where <where> --recorded-by <agent>` for one that drives review, with the verdict given as `--verdict` on the close, which SHALL be required there and SHALL never be read from the words; `--words`, `--where` and `--recorded-by` SHALL carry the relay's words, place and recording agent, so SpecSync's approval and review record the relayed decision. A human decision that is neither an approval nor a review, such as a request for changes, SHALL be recorded with `--no-native`, which closes the gate with the relay and runs nothing; Chough SHALL NOT decide which case applies from the words. ### REQ-records-014

Chough's records stay out of SpecSync's verification. The folders Chough writes while work is in progress, `.chough/sessions/`, `.chough/archive/` and `.chough/bugs/`, SHALL hold only Chough's records: no case definition, preference, reading guide or other input that a change's verification needs SHALL be written under them, and `.chough/cases/`, `.chough/preferences.json`, `.chough/README.md` and `knowledge/` SHALL stay outside them. These three prefixes are what a project lists in SpecSync's documented exclusion, `verification_ignored_paths` in `.specsync/sdd.json` (SpecSync 6.1.2 and later), so that a Chough record written after `specsync change check --commit`, whether left untracked or committed, leaves the recorded verification current, in the author's tree and in a reviewer's clean checkout alike; `.chough/local/` is already Git-ignored and never part of it. Chough SHALL read that policy and SHALL never write it: `chough doctor` SHALL report `records_in_verification` (REQ-history-012) while `.specsync/sdd.json` exists and its list lacks any of the three prefixes, naming the missing entries, the SpecSync version that supports them and that adding them is an ordinary reviewed change to `.specsync/sdd.json`; `chough init` SHALL print the same advice; and the migration plan and receipt SHALL list it as a follow-up (REQ-records-009). The spec files read for this advice SHALL be found without following a symbolic link, to a file or to a folder, so a link out of the project cannot make outside code count and a link cycle cannot hang `chough doctor` or `chough init`; the walk SHALL read at most 4,096 entries and 32 folders deep, and when it stops at that bound, the advice SHALL say so, naming the bound, so a root file beyond it is not silently missed (#402). `chough next` SHALL say when Chough writes are safe: with the three entries in force, that Chough's records may be written and committed at any point of the native order; without them, that Chough's records are committed before `change check --commit` and nothing under `.chough/` is written until finalize. ### REQ-records-016

Control characters. A control character is a C0 control (U+0000 to U+001F), DEL (U+007F), a C1 control (U+0080 to U+009F) or a bidirectional override or isolate (U+202A to U+202E, U+2066 to U+2069). Before writing any committed record, Chough SHALL refuse a value a person gives that holds one, in every field REQ-records-006 checks, as `refused:control-character`, naming the field and the character's code point and never the value, with every file byte-identical, under `--redact` too; a line feed SHALL be accepted in a field that accepts a line break, and a carriage return directly before it SHALL be dropped, so a line break pasted from Windows is stored as a line feed (#366). Chough SHALL print text it read from a record or was given, in text and JSON output alike, with each control character escaped as `\u` and four lowercase hex digits, the form JSON uses, so no terminal acts on it, while JSON output still parses back to the stored value; a line feed SHALL be printed as it is where the text is shown on several lines and as `\n` where it is shown on one line, such as the reason on `chough next`'s `Native change: none needed:` line (#366). What Chough generates from stored text, the journal feed `knowledge/journal/feed.xml`, `knowledge/index.md` and an archived story, SHALL hold that text as it is printed, so a post or a record an earlier release wrote leaves the feed well-formed XML and neither file nor the story holds a control character raw (#366). A front matter scalar that a YAML reader takes as other than text, `null`, `~`, `true`, `false`, `yes`, `no`, `on` or `off` in any letter case, SHALL be written double-quoted, so every text field reads back as text (#366). Trace: LIFE-26, LIFE-3.

Acceptance Criteria
- With ESC, BEL, DEL, U+009B, U+202E and U+2066 each in an objective, a decision, a `--no-native-change` reason, a `--pr`, an evidence summary, environment and limitation, a bug title, an inbox entry and relayed `--words`, the write is refused as `refused:control-character` naming the field and the code point, the output holds no control character, and every file is unchanged, with `--redact` as well.
- A decision and an evidence summary holding a line feed are written, while one holding a tab is refused as `refused:control-character` naming U+0009; a CRLF line break is stored as a line feed; `--title` and `--pr` holding a line feed are refused as before; a tab already stored is printed as `\u0009`.
- A fixture holding each control character, written by hand as an earlier release could, in every record kind (session, story, evidence entry, bug, inbox entry, journal post, case definition and gate), and every command in `chough --help`'s tree run over it, in text and JSON where it has both, with the fixture's IDs where a command takes one: no output holds a control character raw, and each JSON output still parses; a command added later is in the sweep without editing it. A `--no-native-change` reason holding a line feed shows on `next`'s line as `\n`.
- With a journal post and a session from an earlier release holding each control character, `chough library index` writes a feed that parses as XML and an index holding none raw, and archiving the session writes a story holding none raw.
- `--no-native-change null`, `--decision true`, `--decision yes`, a blocker `Off` and an objective `~` are written double-quoted and read back as text.
